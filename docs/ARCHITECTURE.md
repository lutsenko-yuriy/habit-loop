# Architecture

Vertical-slice architecture where each slice is a feature from @docs/PRODUCT_SPEC.md, with four layers per slice: domain, application, data, and UI.

Cross-cutting infrastructure (analytics, crashlytics, remote config) lives under `lib/infrastructure/`. Pure domain models and repository interfaces shared across features live under `lib/domain/`.

Product experiments (hypothesis, metrics, decisions) are tracked in `docs/experiments/` — see `docs/experiments/README.md` for the index and `docs/experiments/TEMPLATE.md` for the per-experiment format. Periodic non-mechanical code-quality checkups are tracked in `docs/knowledge/checkups/` — a `README.md` ledger with a per-tier cadence/due table plus open findings, and one dated `CHK-YYYY-MM-DD-<tier>.md` write-up per run, with due status read by `scripts/checkup/due.py`.

## Layers

### Domain (`lib/domain/`)
Pure business models and repository interfaces shared across features. No dependencies on data, UI, infrastructure, or application layers. The canonical vocabulary for these models (pact, showup, schedule, slot, streak, …) is defined in `docs/GLOSSARY.md`.
- Models: `Pact`, `PactStatus`, `Showup`, `ShowupStatus`, `ShowupSchedule`, `PactStats`, `ScheduleType`, `PactBreak` (HAB-195)
- Repository interfaces: `PactRepository`, `ShowupRepository`, `PactBreakRepository`. `PactRepository` additionally exposes `getSuccessor(pactId)` (HAB-202) — returns the pact whose `predecessorPactId == pactId`, i.e. the single successor in a pact chain (`null` if none).
- Sync repository interfaces: `PactSyncRepository`, `ShowupSyncRepository`, `PactBreakSyncRepository` — provide `getDirtyPacts()`/`getDirtyShowups()`/`getDirtyPactBreaks()`, `markPactSynced()`/`markShowupSynced()`/`markPactBreakSynced()`, and `getPactSyncedAt()`/`getShowupSyncedAt()`/`getPactBreakSyncedAt()` (plus `markAllPactsDirty()`/`markAllShowupsDirty()`/`markAllPactBreaksDirty()`, used after a Firebase UID change); implemented by the SQLite repositories; consumed solely by the sync service — view models and application services never depend on these interfaces. `PactBreakRepository` additionally exposes `getBreakById(id)` (WU1.3, HAB-195) so the pull-merge path can look up a break by id the same way `PactRepository.getPactById`/`ShowupRepository.getShowupById` do.
- `Pact.predecessorPactId` (`String?`, HAB-202) — nullable self-reference to the finished pact this one was created from via "Adjust and start again", forming a linear **chain of pacts**. Immutable through ordinary `copyWith` calls (set at creation, never edited by any application-layer caller). `null` = a root/blank-created pact. The forward direction (successor) is not stored on the row — it is derived by querying `predecessorPactId` (`PactRepository.getSuccessor`, also exposed as a thin passthrough on `PactService.getSuccessor` so view models don't depend on `PactRepository` directly). The "at most one successor per pact" invariant is enforced in the data layer (a partial unique index on `predecessor_pact_id WHERE NOT NULL`, plus a `savePact` guard in both repositories), not merely by hiding the UI entry point. No stats/streak carryover — the chain is purely navigational. **`copyWith(clearPredecessorPactId: true)`** (WU3) is the sole exception to "immutable" — reserved for `FirestoreSyncService`'s last-write-wins conflict resolution (see below); `PactMapper.toUpdateRow` includes `predecessor_pact_id` (WU3, previously excluded) since every other caller's `copyWith` leaves the value unchanged, making this a no-op write on every other update path.
- `PactBreak` (`lib/domain/pact/pact_break.dart`, HAB-195) — a user-initiated pause on an active pact: `id`, `pactId`, `startDate`, `plannedEndDate` (`null` = "until pact ends"), mandatory `rationale`, `createdAt`, `stoppedAt` (`null` = not stopped). `stop(now)` writes `stoppedAt` (mirrors `Pact.stop()` — never deleted); `effectiveEnd` = `stoppedAt ?? plannedEndDate`; `contains(scheduledAt)` is the window predicate. **"On break" is derived at read time, never stored on the showup row** — a pending showup is on-break iff its `scheduledAt` falls inside any of its pact's break windows (`BreakDerivation.isShowupOnBreak`, `slices/pact/application/`). Because stopping fixes the window, already-on-break showups stay on-break permanently with no snapshot step. One active/scheduled break per pact at a time.
- Generators: `ShowupGenerator`, `ShowupDateUtils`
- Result types: `SaveShowupsResult`

### Application (`lib/slices/*/application/`)
Orchestration logic that coordinates domain objects and repository calls. Lives inside each slice vertical. May depend on `lib/domain/` and on other slices' application services when necessary (though cross-slice imports should be minimised).
- `PactBuilder` (`slices/pact/application/`) — holds the 7 pact-data fields assembled during the creation wizard, exposes validity predicates (`isDateRangeValid`, `isShowupDurationValid`, `isScheduleSet`, `isHabitNameValid`, `isComplete`), and materialises a `Pact` via `build(id, createdAt, {predecessorPactId})` (HAB-202: `predecessorPactId` is forwarded straight to the built `Pact`, not stored on the builder itself — wizard-navigation/chain-seeding concerns live in `PactCreationState`, not `PactBuilder`).
- `PactChainService` (`slices/pact/application/`, HAB-202) — pure chain-navigation logic for "Adjust and start again". Walks a finished pact's `predecessorPactId` links back to the chain root (via `PactRepository.getPactById`, tolerating a dangling reference by stopping there) to compute both the root pact's current habit name and the number of ancestors `n`, producing the default new-pact name `"<root habit name> (v{n+1})"` (computed once at creation, never recomputed on later renames). Also builds the prefilled `PactBuilder` for the creation wizard — carrying the predecessor's default habit name, schedule (via `PactBuilder.fromPact`'s legacy-schedule migration), showup duration, and reminder offset, but resetting `startDate`/`endDate` to a brand-new pact's defaults (start = today) rather than the predecessor's own dates. Provider: `pactChainServiceProvider` (`app_providers.dart`) — no consumer until WU3/WU4 wire the detail screen's "Adjust and start again" handler.
- `PactCreationConfig`/`pactCreationConfigProvider` (`slices/pact/ui/generic/pact_creation_view_model.dart`, HAB-202) — the seam that hands `PactChainService`'s async prefill to the creation wizard's synchronous `Notifier.build()` (same split the edit flow's own async `load()` uses, just via a provider instead of a family arg since the creation VM isn't keyed by pact id). The caller sets `PactCreationConfig(predecessorPactId, prefillBuilder)` on this `StateProvider<PactCreationConfig?>` immediately before invalidating/pushing the creation screen (mirroring how `dashboard_screen.dart` already invalidates `pactCreationViewModelProvider` before every push); `PactCreationViewModel.build()` reads it once to seed `PactCreationState`. Riverpod forbids a provider from mutating another provider's state during its own `build()`, so the VM cannot auto-clear this config itself — **the caller must reset it back to `null`** once the creation screen is popped, or the next blank creation would inherit a stale prefill.
- `PactCreationState` (`slices/pact/application/`) — wizard-navigation state: holds `builder: PactBuilder`, `currentStep`, `commitmentAccepted`, `isSubmitting`, `submitError`. Re-exports `ScheduleType` for backwards compatibility. HAB-202 added `source` (`blank` | `adjust_and_start_again`, defaults `blank`), `predecessorPactId`, and `prefillBuilder` — all three set once at construction from `pactCreationConfigProvider` and excluded from `copyWith`'s params (structurally immutable after creation, same pattern as `Pact.createdAt`/`predecessorPactId`); `PactCreationViewModel.submit()` reads them to persist the predecessor link and to diff the final builder against `prefillBuilder` for `PactCreatedEvent`'s `*_changed_from_*` analytics flags.
- `PactDetailBundle` (`slices/pact/application/`) — value object holding `Pact pact`, `PactStats stats`, `PactTimelinePage timelinePage`, and `List<PactBreak> breaks` (HAB-195, defaults `const []`) for one pact: the unit cached by `PactDetailCache`. `breaks` is already folded into `stats.skippedOnBreak`; kept on the bundle so a later read surface (e.g. the timeline's break milestone, WU5.1) can render it without a separate fetch.
- **Chain links on the pact detail screen** (HAB-202 WU3, layout revised in WU4) — `PactDetailState` gained `predecessorPact`/`successorPact` (`Pact?`, both nullable), populated by `PactDetailViewModel.load()` via `PactService.getPact(predecessorPactId)`/`getSuccessor(pact.id)` (cheap, uncached, at most one round-trip each — deliberately outside `PactDetailBundle`/`PactDetailCache`, since these are simple lookups, not part of the stats/timeline cache's write-through-refresh contract). `PactDetailPageIos`/`_Android` render "Previous Pact" and "Next Pact" as a `Row` (`MainAxisAlignment.spaceBetween`, `Flexible`-wrapped children so a long habit name ellipsizes instead of overflowing) right under the name/status badge — Previous leading, Next pinned to the trailing edge, each independently gated on its own field being non-null (a mid-chain pact with both a predecessor and a successor shows both simultaneously) — rather than splitting Next Pact off into the bottom action area as WU3 originally shipped it; both links are shrink-wrapped (`TextButton.styleFrom(minimumSize: Size.zero, tapTargetSize: shrinkWrap)` / `CupertinoButton(minimumSize: Size.zero)`, `AppTypography.caption` text) since the default button chrome otherwise dwarfs a single-line secondary link. Both gated on `FeatureFlags.pactChainingEnabled`. Each page's outer `ListView` carries a pact-specific key (`pact-detail-scroll-view-<id>`) so a test can scroll a specific screen's own content into view when more than one `PactDetailScreen` is mounted at once (see below), and an optional `scrollController` (owned by `PactDetailScreen`, not the stateless pages) that `_onAdjustAndStartAgain` uses to `jumpTo(0)` after returning from the wizard — the ListView otherwise keeps whatever offset it had before the push (same still-mounted screen instance throughout), which would leave newly-relevant top-of-list content (a fresh "Next Pact" link) scrolled out of view, and — since a lazy `ListView` doesn't build far-offscreen children — not even *built* yet, not merely offstage. `PactChainLinkTappedEvent` (`pact_id` = the screen the link is shown on, `direction`: `previous`\|`next`) fires on tap. `pact_chaining_enabled` is a Remote Config kill-switch defaulted `false` during the WU3/WU4 rollout, flipped to `true` at the end of WU4 (the live Firebase console value must be updated manually to match — see `docs/FEATURE_TOGGLES.md` and the Remote Config sync-gap note in `docs/knowledge/notes/HAB-202.md`).
- **`PactDetailScreen.cameFromPactId`** (HAB-202 WU3) — nullable `String?` route param, `null` unless the screen was pushed by tapping a chain link. `_onOpenChainLink(targetPactId)` pops back to the existing page instance if `targetPactId == cameFromPactId` (the user is bouncing back the way they came), otherwise pushes a new `PactDetailScreen(pactId: targetPactId, cameFromPactId: <this screen's own pactId>)` — this is what keeps the back stack from growing unbounded when a user bounces between "Previous Pact" and "Next Pact". Because Navigator keeps earlier routes mounted underneath a pushed one (default `maintainState: true`), tests asserting "which pact's screen is currently shown" must not rely on `find.text(habitName)` (it also matches the pacts-panel row still mounted behind the detail screen) — read the topmost mounted `PactDetailScreen.pactId` instead, and use `pumpAndSettle()` rather than a fixed-duration pump so a push/pop transition fully finishes (and the popped screen is actually removed from the tree) before asserting.
- **"Adjust and start again" action** (HAB-202 WU4, final WU) — `PactDetailScreen._onAdjustAndStartAgain` is the sole consumer of `PactChainServiceProvider`/`pactCreationConfigProvider` wired in WU2/WU3: it fires `PactAdjustAndStartAgainTappedEvent`, reads `pactDetailNowProvider` (not `DateTime.now()` directly, so the prefill's "today" stays overridable in tests), builds the prefilled `PactBuilder` via `PactChainService.buildPrefillFor`, seeds `pactCreationConfigProvider`, invalidates `pactCreationViewModelProvider` (config is read via `ref.read`, not watched, so the VM would otherwise not rebuild), pushes `PactCreationScreen`, then on return resets the config to `null` and reloads the detail state — mirroring `_onStartBreak`/`_onEditPact`'s existing push-then-reload pattern. The button itself (`PactDetailPageIos`/`_Android`) renders as a `FilledButton`/`CupertinoButton.filled` (a "button", not the Previous/Next links' shrink-wrapped `TextButton`/`CupertinoButton` "link" treatment, matching the spec's own wording) alone in the bottom action area, gated on `pact.status != PactStatus.active && state.successorPact == null` — "Next Pact" lives with "Previous Pact" under the title instead (see above), not here, so this button and that link never compete for the same spot. No divider precedes it (unlike the active-pact actions above it) — an earlier attempt added one and pushed the block past the reachable scroll extent on a short viewport, breaking WU3's own nav-stack scenarios; this is a real constraint on this block's height, not a stylistic choice. `PactWizardAbandonedEvent` gained an optional `source` field (only set from the creation screen, never the edit screen) so an abandoned adjust-flow is distinguishable in analytics from an abandoned blank creation.
- **Chain sync-conflict resolution** (HAB-202 WU3, `FirestoreSyncService._resolvePredecessorConflict`) — guards `_mergeRemotePact`'s insert path: if two offline devices each independently create a successor for the same predecessor, `savePact`'s "at most one successor" guard would otherwise throw on the second one's pull-merge insert, silently swallowed by `pullRemoteChanges`'s per-record try/catch — permanently hiding the losing record even though it still exists in Firestore and on its origin device. Last-write-wins on `createdAt` (falling back to `startDate`, matching `Pact.createdAt`'s own documented convention for pre-dated pacts): whichever successor was created later keeps its link; the other has `predecessorPactId` cleared via `copyWith(clearPredecessorPactId: true)` — the record itself is never dropped, it just surfaces as unlinked.
- `PactDetailCache` (`slices/pact/application/`) — session-scoped, injectable, single population/write-through entry point for a pact's stats + timeline + metadata together (HAB-174). Replaces the earlier separate `PactTimelineCache` and `PactStatsService`'s private `_statsCache` — that two-cache design (HAB-126, canceled) let a shared read path (`syncStats`) bypass the timeline cache and desync the two. Holds `Map<String, PactDetailBundle>` keyed by `pactId`. `load(pactId, {now})` — cache hit returns the stored bundle immediately, no DB call and no recompute; cache miss fetches `Pact` + `List<Showup>` + `List<PactBreak>` (HAB-195) once, computes the bundle (stats via a single forward pass over the sorted showup list that also buckets tail/non-tail milestones — see `pact_detail_cache_test.dart` for the golden-equivalence check against `PactStats.compute`/`PactTimelineGrouper.group`; `skippedOnBreak` is derived separately from the same sorted list via `BreakDerivation`, since `PactTimelineGrouper.groupWithStats` only merges breaks into the milestone list, not the pending-showup stats pass — WU5.1, HAB-195), stores, and returns. On a cache miss with an empty showup list and a non-null `Pact.stats`, the frozen stats snapshot is used instead of recomputing from nothing — a rare edge case since HAB-208 (a pact stopped before its first showup ever occurred, so there's genuinely nothing to recompute from); `stopPactTransaction` no longer deletes a stopped pact's *past* showups, only its future ones. `peek(pactId)` — synchronous, cache-only, no fetch; used by `PactTimelineViewModel.build()` to seed the Timeline screen's title from the pact name without a forwarded navigation argument. `refresh(pactId, {pact, showups, reuseCachedShowups, breaks, reuseCachedBreaks, now})` — the one write-through entry point: skips the DB fetch for whichever of `pact`/`showups`/`breaks` the caller already has in hand (reusing the previously cached showup/break list when only `pact` changed, e.g. a note edit, via the explicit `reuseCached*` opt-ins), recomputes, and overwrites the entry unconditionally. Both `showups` and `breaks` default to a fresh DB re-fetch when omitted — a caller can never silently serve stale cached data by forgetting an opt-in. `evict(pactId)` — evict-only, for when there is nothing valid left to cache; clears the cached showups and breaks too. Every mutation path (`PactStatsService.persistShowupStatus`/`stopPact`/`persistStats`, `PactService.updatePact`, `PactBreakService.startBreak`/`stopBreak`) goes through `refresh`/`evict` on this one cache — no second, bypassable population path exists.
- `PactStatsService` (`slices/pact/application/`) — owns pact stats calculation and the stop-pact transaction. Holds no cache of its own; delegates all caching to the shared `PactDetailCache`. `currentStats(pact, showups: [], breaks: []})` is async: passing a non-empty `showups` list bypasses the cache and computes fresh stats directly from the provided list (used by `stopPact`'s `existingStats ?? currentStats(...)` fallback) — `breaks` (HAB-195, defaults `const []`) is threaded into that computation only; passing an empty `showups` list reads `(await cache.load(pact.id)).stats`, which is already break-aware regardless of the `breaks` argument since `PactDetailCache` fetches the pact's real breaks itself. `persistShowupStatus({showup, status, redeemable, now})` evicts the cache entry first (so a racing read falls back to DB rather than stale data), then best-effort re-syncs via `syncStats` → `persistStats`, which persists the recomputed stats to the pact row and repopulates the cache via `cache.refresh(pact.id, pact:, showups:, breaks:, now: now)`. `persistStats`'s `breaks` param is nullable (HAB-195) and deliberately **not** defaulted to `const []`: passing `null` (every call site until WU3 wires the dashboard/showup-detail view models through) both persists a conservative `skippedOnBreak: 0` onto the frozen `pact.stats` snapshot *and* omits the `breaks:` argument to `cache.refresh`, so the cache still falls back to its own correct DB fetch — the live read path (`PactDetailCache`, what Pact Detail actually renders from) is always correct; only the rarely-read frozen snapshot lags until a caller supplies real breaks explicitly. `stopPact()` calls `cache.evict(pactId)` after the transaction deletes the pact's showups. **`now` is threaded through from the caller** (`DashboardViewModel`'s `todayProvider`, `ShowupDetailViewModel`'s `showupDetailNowProvider`) rather than left to default to `PactDetailCache`'s real-wall-clock fallback (HAB-174 WU3 finding): once `PactTimelineViewModel` reads from this same shared, session-persistent cache, a write-through repopulation that silently used the real clock instead of the app's overridden/frozen "now" would mis-bucket the cached `PactTimelinePage`'s tail zone — surfaced by an integration test where a dashboard gap-fill sweep (auto-failing backfilled showups) repopulated the cache before Timeline ever read it.
- `PactTransactionService` (`slices/pact/application/`) — owns the atomic write paths that span both `pacts` and `showups` tables. `savePactWithShowups(pact, showups)` inserts both in one SQLite transaction and sets `total_showups` to `showups.length`. `stopPactTransaction(updatedPact, pactId, now)` updates the pact row and deletes only the pact's showups scheduled after `now` in one SQLite transaction — showups at or before `now` are real history and are kept so stats and the timeline stay intact after stopping (HAB-208). Both methods use `ConflictAlgorithm.fail` so any duplicate-ID error surfaces immediately rather than silently overwriting data. Provider declared in `lib/infrastructure/injections/app_providers.dart`. `pactServiceProvider` and `pactStatsServiceProvider` both watch `pactDetailCacheProvider` directly rather than depending on each other — `PactService.updatePact(pact, {now})` calls `PactDetailCache.refresh(pact.id, pact: pact, reuseCachedShowups: true, now: now)` unconditionally on every update (this replaced a narrower `PactStatus.completed`-only `PactStatsService.onPactCompleted` call, which no longer exists; `reuseCachedShowups` is safe here since `updatePact` never changes a pact's showups; `now` is forwarded from the caller for the same reason as `persistShowupStatus` above). Depending on the shared cache instead of on each other avoids the circular-dependency risk the codebase has flagged before.
- `PactTimelineConfig` (`slices/pact/application/`) — resolves `noGroupingTailPeriodInDays` (`pact_timeline_no_grouping_tail_period_in_days`) from `RemoteConfigService`. Kill-switch flag: `pact_timeline_enabled` (default `true`). **No pagination fields** — an earlier design (`first_page_size`/`nth_page_size`) was dropped during HAB-116 because paging and grouping interact non-obviously (the grouper needs the full showup list to compute tail zones and streaks correctly); see `docs/knowledge/notes/HAB-116.md`.
- `PactTimelineGrouper` (`slices/pact/application/`) — pure, stateless grouping algorithm operating on a list of `Showup` domain objects, sorted ascending by `scheduledAt`. Single forward pass over the list fuses tail-zone bucketing with non-tail streak construction, partitioning showups into `PactTimelineMilestone` milestones: streak milestones (same-outcome run of 2+ outside the tail zone), single-showup milestones (a run of 1, or any done/failed showup inside the tail zone), and noted-showup milestones (always individual, tail or not). Removed the dead grouping-threshold machinery (HAB-177) — the Remote Config default had been 1 in every real build, making the old two-pass group/streak split a no-op. Has no I/O dependencies — fully unit-testable. `group()` returns `({milestones, tailStartIndex})`; `groupWithStats()` (HAB-174 WU1.1) is the same forward pass additionally tallying `showupsDone`/`showupsFailed`/a running trailing-done streak over the same resolved (non-pending) showups it already visits, returning `({milestones, tailStartIndex, showupsDone, showupsFailed, currentStreak})` — `group()` is now a thin wrapper over it. Lets `PactDetailCache` compute stats and the timeline in one pass instead of two (`PactStats.compute` + `group()` back-to-back); `group()`'s own return shape is unchanged so existing exact-shape record destructuring of it elsewhere is unaffected. Both methods take an optional `breaks` param (WU5.1, HAB-195; restructured HAB-216, defaults `const []`): every showup covered by a break — any status, tail zone or not — merges into a single `BreakMilestone` instead of flowing through the streak/single/tail-zone logic. `coveringBreak` is computed for every non-future showup, not just pending ones, so an explicit `done`/`failed` mark inside a break window doesn't escape the merge and split the run (a deliberate render/stats divergence: the mark still counts toward `showupsDone`/`showupsFailed`/the trailing streak exactly as it would outside a break — only rendering merges it). A break run is split into its own entry whenever the covering break changes, so two adjacent breaks never merge into one. `tailStartIndex` — normally claimed eagerly at the first tail-zone item — is instead resolved lazily at the break run's *flush* time via a `touchesTail` accumulator flag, since a boundary-spanning run doesn't know whether it will reach the tail until it gets there; this still costs one forward pass, not two. A showup only merges into a break run once its own calendar day has arrived (`scheduledAt`'s day `<= today`) — `TailZone.contains` has no upper bound (by design, for redemption eligibility), so without this guard a break spanning into the future would leak those not-yet-happened dates onto the timeline; an ordinary future pending showup never had this problem since it's unconditionally skipped regardless of tail-zone membership. More generally, **no showup of any status appears on the timeline once its calendar day is after today** (a `showup.scheduledAt`-day-`> today` guard right before milestone emission, checked for every status, not just pending/on-break) — an explicit done/failed mark always overrides a break and nothing stops marking a not-yet-due showup early, so this covers a manually-resolved future showup too. The guard sits *after* the `showupsDone`/`showupsFailed`/trailing-streak counters update but *before* tail-zone/streak-accumulation, so those stats are unaffected (unchanged, pre-HAB-195 behaviour) — only the milestone list itself hides future dates.
- `PactTimelineMilestone` (`slices/pact/application/`) — sealed union of seven milestone kinds: `PactCreatedMilestone`, `ShowupStreakMilestone`, `NotedShowupMilestone`, `SingleShowupMilestone`, `BreakMilestone`, `CurrentStateMilestone` (active pacts), `PactConcludedMilestone` (stopped/completed pacts — `note` mirrors `Pact.stopReason`, so editing the pact-level note is Timeline-visible for concluded pacts). `BreakMilestone` (HAB-216) carries the covering `PactBreak` plus the covered-showup range (`firstAt`/`lastAt`, `count`) and replaces the earlier `isOnBreak`/`breakRationale` fields WU5.1 (HAB-195) had added to `ShowupStreakMilestone`/`SingleShowupMilestone` — every showup covered by the same break now merges into one non-tappable entry regardless of outcome or tail-zone boundary, rather than an on-break run painting blue within the ordinary streak/single grouping. Named "milestone" to distinguish from analytics events (`PactCreatedEvent` etc.) and from UI list items. Anchor milestones (pact created, current state / concluded) are always visible outside the tail-zone section.
- `PactTimelinePage` (`slices/pact/application/`) — value object built by `PactDetailCache` as part of a `PactDetailBundle`: `anchorStart` (`PactCreatedMilestone`), `anchorEnd` (`CurrentStateMilestone` or `PactConcludedMilestone`), `milestones` (all grouped showup milestones, oldest-first), `tailPeriodInDays`, and `tailStartIndex` (the index in `milestones` where the tail zone begins — must be used to place the section header rather than inferred by searching for `SingleShowupMilestone`, which also appears outside the tail zone). There is no pagination — the whole showup history is loaded and grouped once per cache population, and the UI renders it in full (no "Load more" control exists).
- `PactBreakService` (`slices/pact/application/`, WU2, HAB-195) — owns the break lifecycle. `getActiveBreak(pactId, {now})` returns the single break that currently blocks starting a new one — the one *unresolved* (active-or-scheduled) break, i.e. `!PactBreak.isResolved(now)`, found via a linear scan of `getBreaksForPact`'s oldest-first list; at most one can exist at a time. `startBreak({id, pactId, startDate, rationale, now, plannedEndDate})` throws `ArgumentError` if `rationale` is empty/whitespace-only (the mandatory-rationale product rule enforced at the service boundary, not just in the UI form) and `StateError` if `getActiveBreak` already finds one; on success it persists via `PactBreakRepository.saveBreak`, fire-and-forgets `SyncService.uploadPactBreak`, cancels reminders (`ReminderSchedulingService.cancelRemindersForShowup`) for every pending showup the new break's window now covers (found via `BreakDerivation.isShowupOnBreak(showup, [pactBreak])` over `ShowupRepository.getShowupsForPact`), and evicts the pact's `PactDetailCache` entry. `stopBreak(breakId, {now})` — "Resume pact" — throws `ArgumentError` if no break with that id exists; otherwise calls `PactBreak.stop(now)`, persists via `updateBreak`, uploads, and evicts the cache. Neither method schedules/restores reminders going forward or touches auto-fail — that suppression-side wiring (`DashboardViewModel`'s sweeps, `ShowupDetailViewModel`'s late-open path, `ReminderSchedulingService.scheduleRemindersForShowups`) is WU3. `BreakDerivation` (`lib/domain/pact/break_derivation.dart`) is the pure on-break predicate reused by most read surfaces (dashboard dots, showup detail, stats): `isShowupOnBreak({showup, breaks})` is `false` for any resolved (`done`/`failed`) showup — an explicit mark always overrides a break — and otherwise `true` iff some break's `contains(showup.scheduledAt)`. The timeline is the one exception (HAB-216): `PactTimelineGrouper` computes its own `coveringBreak` directly rather than calling `BreakDerivation`, and the two predicates deliberately disagree on a resolved showup — the grouper still merges it into the covering `BreakMilestone` (see above) where `BreakDerivation` would say "not on break". `PactStats` gains a `skippedOnBreak` count (defaults `0`) derived from break windows via `compute`'s optional `breaks` param; `fromCounts` threads it straight through. Provider: `pactBreakServiceProvider` (`app_providers.dart`), composed from `pactBreakRepositoryProvider`, `showupRepositoryProvider`, `reminderSchedulingServiceProvider`, `syncServiceProvider`, and `pactDetailCacheProvider` — no `AppContainer.overrides` change needed, since all of its dependencies were already overridable.
- `ShowupGenerationService` (`slices/showup/application/`) — orchestrates lazy windowed showup generation and deduplication.

**Strict layer rule:** UI view models (`lib/slices/*/ui/`) must never import `PactRepository`, `ShowupRepository`, or any other repository interface directly. All reads and writes go through an application service. The only exception is `slices/debug/ui/` (release-excluded tooling).

**Cross-slice signals:** When one slice needs to notify another of a state change (e.g. pact created → dashboard must reload), it must not import the target slice's view model. Instead, post to a lightweight `StateProvider<int>` signal owned by the target slice and exposed from a dedicated `*_refresh_signal.dart` file. The target slice's view model listens to the signal in `build()` and reacts internally. Example: `dashboardRefreshSignalProvider` in `slices/dashboard/ui/generic/dashboard_refresh_signal.dart` — the pact and showup slices increment it after mutations; the dashboard VM invalidates `hasActivePactsProvider` and calls `load()` in response.

### Theme

`lib/theme/` contains the cross-platform Habit Loop visual foundation: the shared brand palette and the Material/Cupertino theme data applied from `HabitLoopApp`. Feature UI should consume the theme via `Theme.of(context)`, `CupertinoTheme.of(context)`, or the shared semantic colors when a reusable status color is needed. Launcher icon assets under `assets/app_icon/`, `ios/Runner/Assets.xcassets/AppIcon.appiconset/`, and `android/app/src/main/res/mipmap-*/` use the same palette so the installed app icon matches the in-app design language.

`lib/theme/widgets/` holds domain-agnostic presentational widgets used by more than one feature slice — currently `StatusBadge`, `SectionHeader`, `DateRowTile`, `AnimatedReveal`, and `AnimatedValueTransition` (HAB-206 WU3; a generic slide+fade crossfade wrapper, placed here despite its only current caller being the pact slice, since it has no domain coupling). Any purely decorative, parameter-driven widget that would create a cross-slice dependency if kept inside a single slice belongs here.

- `AnimatedReveal` (HAB-195 WU4.1 polish) — shows/hides a child by driving its reported height (via `Align.heightFactor`) and its opacity from the *same* `AnimationController` value every frame, so a sibling positioned after it in a list shifts in lock-step with the fade. Deliberately does not clip (unlike `AnimatedSize`/`SizeTransition`): the collapsing child keeps painting at its natural size while its reported height shrinks, so a widget painted after it in the same list visually overlaps the still-fading content instead of the transition looking like an opaque panel sliding over it. First used for the break-creation screen's end-date row/"No end date yet" toggle (`pact_break_creation_page_ios.dart`/`_android.dart`) — composing `AnimatedSize` around `AnimatedSwitcher` was tried first, but that pairing doesn't actually stay synchronized: `AnimatedSize`'s target only changes once the switched-out child is removed from the tree at the *end* of `AnimatedSwitcher`'s fade, so the visible effect was fade-then-shift, not simultaneous.

`lib/theme/spacing.dart` (`AppSpacing`) and `lib/theme/typography.dart` (`AppTypography`) are bare `abstract final class` constant scales (spacing: a numeric `s2`-`s32` scale, each constant named after its own value; typography: a shared `CupertinoTextThemeData` wired into `HabitLoopTheme.cupertinoTheme`) — introduced to replace screen-by-screen hardcoded `EdgeInsets`/`TextStyle` values, starting with the iOS widgets that had none (HAB-187). Not a `ThemeExtension`: spacing and type scale don't vary by brightness/theme in this app today, so bare constants avoid the `BuildContext`-lookup ceremony a `ThemeExtension` would add at each of the ~20 call sites this migration touches.

### Infrastructure (`lib/infrastructure/`)

Cross-cutting services (analytics, crashlytics, logging, notifications, remote config, sync) that are shared by the entire app. Each service follows the same internal structure: `contracts/` (abstract interface with a no-throw contract) and `data/` (production implementation + noop fallback). Provider declarations have been consolidated — see Injections below.

Each slice vertical may contain an `analytics/` subdirectory (e.g. `slices/pact/analytics/`, `slices/showup/analytics/`) with event classes extending `AnalyticsEvent`. This keeps event definitions co-located with the domain they describe.

**Injections:** `lib/infrastructure/injections/` is the single composition root. `app_providers.dart` declares every app-wide Riverpod provider (repositories, transaction service, application services, and all infrastructure service providers including `notificationServiceProvider`). `app_container.dart` exposes `AppContainer.overrides(...)`, a static factory that accepts already-constructed production instances and returns the `List<Override>` passed to `ProviderScope` in `main.dart`. `main.dart` retains all `kReleaseMode` branching and Firebase construction; `AppContainer` is mode-agnostic and purely maps instances to overrides.
**Analytics:** `lib/infrastructure/analytics/` contains the abstract base class (`AnalyticsEvent`, `AnalyticsScreen`), service interface (`AnalyticsService`), Firebase adapter, noop adapter, and Riverpod provider. It has no `ui/` directory because it contains no widgets.

**Auth:** `lib/infrastructure/auth/` provides anonymous Firebase Auth with optional Google account linking.

- `AuthService` — no-throw contract on `initialize()`/`signOut()`; `linkWithGoogle()` may throw `FirebaseAuthException` (callers handle it).
- `FirebaseAuthClient` — intermediate adapter interface isolating all Firebase/Google Sign-In SDK types, so test fakes implement it without importing the SDKs. `FirebaseAuthClientAdapter` wraps `FirebaseAuth` and `GoogleSignIn.instance` (v7.x singleton API), only instantiated in `main.dart`.
- `initialize()` calls `signInAnonymously()` if no user is cached, so every install has a Firebase UID from first launch; fire-and-forget in `main.dart` so it doesn't block `runApp`. `authStateChangesProvider` is a `StreamProvider<AuthState>` re-emitting on Firebase Auth state changes.
- `LocalAuthService` (debug/profile only) — stateful fake: auto-signs-in as `LocalAuthService.localUserId` (`'local_user_id'`) on `initialize()` so QA is signed in on every restart without a manual "Sign in with Google" tap; `signOut()` reverts to anonymous; `linkWithGoogle()` signs back in. Wired when `debug_backend = 'local'` so QA can exercise the full sync flow without a Firebase project.

**Device ID:** `lib/infrastructure/device/` provides a stable per-install UUID. `SharedPreferencesDeviceIdService` generates a UUID v4 on first call, persists it under the `habit_loop_device_id` key, and returns the same value on all subsequent calls. The device ID is used to prefix new pact IDs (`{deviceId}-{uuid}`) for global uniqueness across devices, making multi-device sync conflict-free.

**Crashlytics:** `lib/infrastructure/crashlytics/` wraps crash reporting. Activation is gated on `kReleaseMode` in `main.dart`, so debug and test runs fall back to `NoopCrashlyticsService`. The `CrashlyticsService` interface has a strict no-throw contract: implementations must swallow any exceptions raised by the underlying SDK so that crash reporting failures can never crash the app themselves. The interface exposes `log()` for breadcrumbs and `setCustomKey()` for runtime context (active pact count, current screen, locale). The raw `FirebaseCrashlytics` SDK is referenced in `main.dart` in two ways: via `FirebaseCrashlyticsClientAdapter` for the Riverpod provider override, and directly in the `FlutterError.onError` / `PlatformDispatcher.instance.onError` global error handlers (which must be installed before `runApp`, before the Riverpod container exists). The rest of the app depends only on the abstract interface.

**Logging:** `lib/infrastructure/logging/` provides structured local logging via `talker_flutter`. The `LogService` interface exposes `debug()`, `info()`, `warning()`, `error()`, and `logLocal()` (for PII-safe local-only detail). `TalkerLogService` is active in debug and profile builds only; `NoopLogService` is the default in release and tests. The in-app log overlay is gated on `kDebugMode`. **PII rule:** never pass user-entered text (habit names, notes, stop reasons) to `CrashlyticsService` — only field lengths, IDs, counts, and enum values. Local `logLocal()` calls may include more detail since logs never leave the device.

**Firestore:** `lib/infrastructure/firestore/` wraps the Firestore remote storage layer.

- `FirestoreClient` — abstract, no-throw interface; methods accept only plain `Map<String, dynamic>` (no SDK types leak through — test fakes implement it without importing `cloud_firestore`).
- Schema: flat, mirrors local SQLite — `/users/{userId}/pacts/{pactId}`, `/users/{userId}/showups/{showupId}`, `/users/{userId}/pact_breaks/{pactBreakId}` (WU1.3, HAB-195).
- `NoopFirestoreClient` is the default; `FirebaseFirestoreClientAdapter` (wraps real `cloud_firestore`, only instantiated in `main.dart`) is wired in all build modes via `firestoreClientProvider` (same optional-override pattern as other infrastructure providers).
- `fakeFirestoreClientProvider` is a separate `Provider<Object?>` — typed `Object?` so `app_providers.dart` has no import-time dependency on the debug-only `FakeFirestoreClient` class; debug-only call sites cast to `FakeFirestoreClient?`.

Debug/profile-only QA tooling (invisible in release — never constructed under `kReleaseMode`):
- `FakeFirestoreClient` + `FakeFirestoreSeedData` — in-memory client seeded from a `Map<String, dynamic>` snapshot, so the pull/merge path can be exercised end-to-end against deterministic remote data.
- `FaultInjectingFirestoreClient` — decorator reading connectivity mode from `RemoteConfigService` per call: `'absent'` always throws, `'unstable'` throws probabilistically (`debug_connectivity_stability_percent`), `'perfect'` passes through. Lets QA verify circuit-breaker transitions and partial-failure handling by flipping the mode in the RC overrides screen, no restart needed.
- `debug_backend` RC key (`'real'`/`'local'`) selects the wiring: `'local'` → `FaultInjectingFirestoreClient(inner: FakeFirestoreClient)` + `LocalAuthService`; `'real'` → live Firebase stack.

**Sync:** `lib/infrastructure/sync/` contains the circuit breaker and write-through sync service.

*Circuit breaker* (`SyncCircuitBreaker`, `StateNotifier<SyncCircuitBreakerState>`):
- States: `closed` (flowing) → `halfOpen` on any failure → `closed` on success or `open` after N consecutive failures (N = `sync_max_consecutive_failures` from Remote Config, default 5) → `halfOpen` only via `triggerManualSync()` (sync-status UI).
- In-memory only; resets to `closed` on app restart. Failure threshold is read once at provider init from `remoteConfigServiceProvider` (tunable in the Firebase console, no release needed).
- `currentState` getter exposes state to external callers without exposing the `@protected` `state` field.

*Sync service* (`SyncService`, no-throw interface): `uploadPact`, `uploadShowup`, `uploadPactBreak` (WU1.3, HAB-195), `flushDirtyRecords`, `triggerManualSync`, `pullRemoteChanges`. `NoopSyncService` is the const default.

`FirestoreSyncService` (production):
- Checks `canRequest` before each upload; marks synced on success; records success/failure on the CB; fires `unawaited(flushDirtyRecords())` on halfOpen→closed; skips uploads when `userId` is null.
- `pullRemoteChanges()` merges remote pacts/showups/pact breaks into local SQLite via last-writer-wins: not-in-local → insert + mark synced; local dirty → keep local; remote `updated_at` > local `synced_at` → overwrite + mark synced; otherwise → keep local. Runs only when CB is fully `closed` (not just `canRequest`); calls `recordFailure()` on network errors; per-record decode errors are isolated so one bad document never blocks others. All three entities share a single generic `_mergeRemoteRecord<T>` helper parameterized by `getLocal`/`getSyncedAt`/`fromDocument`/`insert`/`update`/`markSynced` (plus an optional `existsGuard`, used only by showups to guard a TOCTOU window against `stopPactTransaction`).
- `PactSyncRepository.getPactSyncedAt()` / `ShowupSyncRepository.getShowupSyncedAt()` / `PactBreakSyncRepository.getPactBreakSyncedAt()` return the local `synced_at` timestamp (or null when dirty) — used exclusively by the pull merge logic.
- `SyncMapper` maps domain objects ↔ Firestore maps, carrying `updated_at` for merge decisions and excluding SQLite-only columns (`dirty`, `synced_at`, `total_showups`).
- `ForceSyncResult` (`forceSyncAll()`'s return type) carries a `pactBreaksFailed` count alongside `pactsFailed`/`showupsFailed`, defaulting to `0` so existing call sites that construct it without the field are unaffected.

Write path: `PactService.createPact`/`updatePact` and `PactStatsService.persistStats`/`persistShowupStatus`/`stopPact` all fire `unawaited(_syncService.uploadPact/uploadShowup)` after every successful local write — sync never blocks the local path. `pullRemoteChanges()` runs fire-and-forget from `main.dart` after `authService.initialize()`. `syncServiceProvider` self-composes from existing providers — `pactRepositoryProvider`/`showupRepositoryProvider`/`pactSyncRepositoryProvider`/`showupSyncRepositoryProvider` need no `AppContainer.overrides` change; `pactBreakRepositoryProvider`/`pactBreakSyncRepositoryProvider` were added as new optional `AppContainer.overrides` params (WU1.3) purely so `main.dart` can wire the real `SqlitePactBreakRepository` in production — the providers themselves still resolve without an override (see the `SqlitePactBreakRepository` note above).

**Persistence:** `lib/infrastructure/persistence/` contains the database lifecycle manager and the codec/mapper utilities used by the SQLite repository implementations.

- `HabitLoopDatabase` owns the sqflite `Database` singleton for production. `runMigrations` (full current schema) and `runUpgradeMigrations` (incremental upgrades) are public statics so tests can apply them to in-memory `databaseFactoryFfi` databases without the file-backed singleton; `@visibleForTesting openForTesting()` is a convenience wrapper. Current schema version: **6** (v2 added `dirty`/`synced_at` to `pacts`/`showups`; v3 added `archived` to `pacts`; v4 added `redeemable` to `showups`; v5 added the `pact_breaks` table — `id`, `pact_id` FK, `start_date`, `planned_end_date` nullable, `rationale`, `created_at`, `stopped_at` nullable, plus `dirty`/`synced_at` sync columns — HAB-195; v6 added `predecessor_pact_id` (nullable `TEXT`) to `pacts` plus a partial unique index `idx_pacts_predecessor_pact_id ON pacts(predecessor_pact_id) WHERE predecessor_pact_id IS NOT NULL` enforcing "at most one successor" — deliberately **no** self-referential FK, so a Firestore pull that delivers a successor before its predecessor can't trigger an FK violation — HAB-202). `PactBreakMapper` (`persistence/`) does row ↔ domain conversion following the same epoch-ms local-time convention as `PactMapper`/`ShowupMapper`; `SqlitePactBreakRepository` (`slices/pact/data/`) implements both `PactBreakRepository` and `PactBreakSyncRepository`.
- `ScheduleCodec`, `PactMapper`, `ShowupMapper` — `abstract final` classes, `static`-only methods, no sqflite dependency of their own (sqflite is introduced by the concrete repositories in `slices/*/data/`).
- `ScheduleCodec` encodes/decodes `ShowupSchedule` discriminated unions to/from the `schedule TEXT` column's JSON string; `decode` applies a type guard before the `Map<String, dynamic>` cast, so a syntactically valid but non-object JSON value produces a `FormatException` rather than an uncaught `TypeError`.
- `PactMapper`/`ShowupMapper` convert domain objects to column maps (`INSERT`/`UPDATE`) and back from row maps (`SELECT`). `toRow()` always writes `dirty = 1` and `synced_at = null`, queuing every local write for the next sync pass; `fromRow()` intentionally ignores both columns — sync state is internal to the repository layer and never surfaced on domain models.
- All `DateTime` fields are stored as epoch milliseconds and reconstructed as **local-time** values, matching the local-time `DateTime` objects produced by `PactBuilder` and `ShowupGenerator` — so timezones are handled correctly throughout the app.

**Onboarding:** `lib/infrastructure/onboarding/` provides the write-once flag that tracks whether the user has completed onboarding (i.e. has seen the dashboard at least once). `OnboardingPreferenceService` is the abstract interface exposing `isOnboardingPassed` (synchronous `bool` getter) and `markOnboardingPassed()` (async, no-throw). `SharedPreferencesOnboardingService` reads synchronously from the SharedPreferences in-memory cache (loaded by `SharedPreferences.getInstance()` before `runApp`) — so the carousel vs. dashboard routing decision is available on the first frame with no I/O. The flag is written once by `DashboardScreen` (via a post-frame callback) the first time the dashboard is shown. `NoopOnboardingService` always returns `false` and is the safe default for tests. The key used is `habit_loop_onboarding_passed`, following the `habit_loop_*` prefix convention.

**Notifications:** `lib/infrastructure/notifications/` wraps local notification scheduling via `flutter_local_notifications`. The `NotificationService` interface has a strict no-throw contract: all implementations must swallow exceptions internally so a notification failure can never crash the app. `FlutterLocalNotificationService` is the production implementation; it uses `zonedSchedule()` with `TZDateTime` (from the `timezone` package) for DST-safe scheduling, and `flutter_timezone` to resolve the device's current IANA timezone at runtime. Notification IDs are derived deterministically from `scheduledAt.millisecondsSinceEpoch ~/ 1000` (no mapping table needed). An in-memory `_pactNotificationIds` registry (pact ID to set of notification IDs) supports `cancelAllRemindersForPact()` without iterating the OS pending-notification list; on app restart the registry is empty and cancellation falls back to `getPendingNotifications()` filtered by the `pactId` field in each notification's payload JSON. The Android notification channel ID is `showup_reminders`. The `onDidReceiveNotificationResponse` callback is wired to `NotificationRouter.navigateToShowup` for deep-link routing; cold-start taps are deferred via `addPostFrameCallback` so the navigator is guaranteed to be mounted. `UNUserNotificationCenter.current().delegate = self` is set in `AppDelegate.swift` before `super.application(...)` because Flutter 3.x no longer sets it automatically. `FlutterLocalNotificationService` is used in **all build modes** (debug, profile, release) so notification navigation can be tested with plain `flutter run`; unit tests are unaffected because they never call `main()` and override `notificationServiceProvider` directly. The provider `notificationServiceProvider` defaults to `NoopNotificationService` and is overridden in `main.dart` via `AppContainer.overrides(...)`.

**Remote Config:** `lib/infrastructure/remote_config/` wraps feature flag resolution.

- `RemoteConfigService` — strict no-throw contract; implementations must swallow exceptions internally so a Remote Config outage can never crash the app.
- `FirebaseRemoteConfigClient` (in `data/`) — intermediate adapter interface returning only plain Dart primitives, so test fakes can implement it without importing `firebase_remote_config`. The raw SDK is confined to `FirebaseRemoteConfigClientAdapter`, only instantiated in `main.dart`.
- Activation gated on `kReleaseMode`: debug/profile use `NoopRemoteConfigService` (in-code defaults from `RemoteConfigDefaults`) and set the fetch interval to `Duration.zero` so QA can verify flag changes without the 12-hour production throttle.
- **Debug overrides:** in debug/profile, `main.dart` wraps the active service in `OverridableRemoteConfigService`, which checks `SharedPreferencesRemoteConfigOverrideStore` (key prefix `rc_override_`) before delegating to the inner service — runtime override of any key without touching the Firebase Console. Managed via `RemoteConfigOverridesViewModel` and the debug UI in `slices/debug/`. Invisible in release builds (`NoopRemoteConfigOverrideStore` default; `OverridableRemoteConfigService` never constructed).

**Feature Flags:** `FeatureFlags` (`contracts/feature_flags.dart`) is a pure value object built from a `RemoteConfigService` snapshot via `FeatureFlags.fromRemoteConfig(rc)`; it exposes typed boolean getters (one per kill-switch flag) and overrides equality/hashCode so `Provider` consumers can compare snapshots cheaply. Active flags include `pact_timeline_enabled` (HAB-116) — when `false`, the "View timeline" entry point on pact detail is hidden — and `pact_breaks_enabled` (HAB-195) — kill-switch for the pact-breaks feature; defaulted to `false` during development (deliberate deviation from the usual default-true convention, so all break UI/behaviour stayed hidden until the feature was complete) and flipped to `true` in WU6, the final ship WU. `featureFlagsProvider` in `app_providers.dart` self-composes from `remoteConfigServiceProvider`. Call sites read it via `ref.watch(featureFlagsProvider)` and gate UI or logic: when a flag is `false` the corresponding entry point is hidden (language picker) or bypassed (Firestore sync). All flags are registered in `RemoteConfigDefaults.all` with `allowedValues: ['true', 'false']` so the debug RC overrides screen renders a picker for them automatically. The catalogue of active flags and their effects is in @docs/FEATURE_TOGGLES.md.

## Scripts (`scripts/`)

Python utilities for CI, release management, and code-quality tooling. All scripts use the Python stdlib only unless noted.

| Module | Entry point | Purpose |
|---|---|---|
| `scripts/changelog/` | `lint.py`, `distribute.py`, `release_notes.py` | CHANGELOG linting, build-skip gate, and "What's New" generation |
| `scripts/ci/` | `dispatch_plan.py` | Translates `workflow_dispatch` inputs into per-job CI flags |
| `scripts/firebase/` | `cleanup_builds.py` | Deletes old Firebase App Distribution releases, keeping the N most recent |
| `scripts/appstore/` | `testflight_upload.sh` | Uploads a signed IPA to TestFlight (internal testing) via `xcrun altool --upload-app` and an App Store Connect API key — runs alongside, not instead of, Firebase App Distribution (HAB-167) |
| `scripts/dead_code/` | `check.py` | Advisory dead-code detector — runs all four detectors in order and prints a report; always exits 0 (never blocks CI or commits). Invoked via the `/dead-code-check` skill or manually. |
| `scripts/checkup/` | `due.py` | Reads the cadence/due table in `docs/knowledge/checkups/LEDGER.md` and reports which tier(s) (light/heavy) are due for review this period. Consumed by the `/checkup` skill and at session start. |
| `scripts/notes/` | `index.py` | Parses `bookmarks:` frontmatter across `docs/knowledge/notes/*.md`, regenerates the generated `INDEX.md`, and validates bookmarks against `docs/knowledge/notes/BOOKMARKS.md`. `--check` blocks CI when a note is missing its `bookmarks:` key or uses a bookmark outside the vocabulary (an explicit `bookmarks: []` passes — "reviewed, nothing noteworthy"); `--apply-bookmarks` does the one-time corpus backfill insert (HAB-221). |

`scripts/dead_code/check.py` detectors (in execution order):

1. **l10n keys** — keys in `lib/l10n/app_en.arb` with no dot-reference (`.keyName`) in any non-generated `.dart` file
2. **Analytics event classes** — `extends AnalyticsEvent` classes with no reference in any `lib/` file (test-only references excluded)
3. **Test/scenario files** — files under `test/` or `integration_test/` whose production imports resolve to non-existent `lib/` paths, or that have zero production imports at all (two severity labels)
4. **Handlers** — `*_handler.dart` files with no importers; `@pragma('vm:entry-point')` top-level functions not referenced in `flutter_local_notification_service.dart`

Tests live in `scripts/dead_code/tests/test_check.py` (stdlib `unittest`, `tempfile` fake project trees — mirrors `scripts/changelog/tests/test_lint.py`).
