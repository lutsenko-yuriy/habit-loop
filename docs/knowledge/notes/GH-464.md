**User decisions that reshaped the brief/plan**

- Selecting a checklist during pact creation was dropped mid-brief: it needs a callback URL, and the wizard has no way to receive one. Selection lives only on pact detail, for active pacts.

**Research-WU findings (topic mode, single pass)**

Q1: `app_links` with UIScene/`FlutterSceneDelegate`. **Use `app_links` ^7.2.2.**
- 7.x adds scene-lifecycle support. The plugin registers itself as a `FlutterSceneLifeCycleDelegate`, reads the initial link from `connectionOptions.urlContexts`, and buffers links until Dart subscribes. Our `SceneDelegate` (subclass of `FlutterSceneDelegate`, calls `super`) needs no change.
- Sources: [CHANGELOG](https://raw.githubusercontent.com/llfbandit/app_links/main/app_links/CHANGELOG.md), [AppLinksIosPlugin.swift](https://github.com/llfbandit/app_links/blob/main/app_links/ios/app_links/Sources/app_links/AppLinksIosPlugin.swift), [README_ios_7](https://raw.githubusercontent.com/llfbandit/app_links/main/doc/README_ios_7.md).
- Cold-start null `getInitialLink` under UIScene was a 6.x bug fixed in 7.0 ([#253](https://github.com/llfbandit/app_links/issues/253), [#209](https://github.com/llfbandit/app_links/issues/209), [#248](https://github.com/llfbandit/app_links/issues/248)). The maintainer recommends subscribing to `uriLinkStream` only, for every case.
- Requires Flutter ≥3.44 / Dart ^3.12 / iOS 13+. That fits: local Flutter is 3.44.0, CI uses `channel: stable`, and the iOS deployment target is 15.0.
- Android: cold start reads the launch intent; warm start uses `onNewIntent` ([AppLinksPlugin.java](https://github.com/llfbandit/app_links/blob/main/app_links/android/src/main/java/com/llfbandit/app_links/AppLinksPlugin.java)).
- Checklister (React Native) opens callbacks via `Linking.openURL`, which always adds `FLAG_ACTIVITY_NEW_TASK` for a different package (`checklister/node_modules/react-native/.../IntentModule.kt`). So the callback is routed to Habit Loop's own task rather than spawning a MainActivity in Checklister's task ([tasks & back stack](https://developer.android.com/guide/components/activities/tasks-and-back-stack)).
- No source confirms the exact `singleTop` + `NEW_TASK` warm-delivery path, so it's a **[human] device check**, not a settled fact. Switching to `singleTask` is the documented fallback if a second instance appears.

Q2: built-in deep linking. **Must be disabled on both platforms.**
- Default flipped to `true` in Flutter 3.27 ([breaking change](https://docs.flutter.dev/release/breaking-changes/deep-links-flag-change)). Our manifests set neither key, so it's currently ON.
- The engine at 3.44.0 still deep-links any URL that a plugin doesn't claim, and app_links defaults to not claiming ([FlutterSceneLifeCycle.mm](https://github.com/flutter/flutter/blob/3.44.0/engine/src/flutter/shell/platform/darwin/ios/framework/Source/FlutterSceneLifeCycle.mm)).
- With our home-only `MaterialApp`, a warm `habitloop://checklist/selected` becomes `pushNamed('/selected')`. That throws "Could not find a generator for route" in debug and fails a null check in release ([app.dart](https://github.com/flutter/flutter/blob/3.44.0/packages/flutter/lib/src/widgets/app.dart); this is from reading the code, no doc states it).
- Fix: add `<key>FlutterDeepLinkingEnabled</key><false/>` to Info.plist, and `<meta-data android:name="flutter_deeplinking_enabled" android:value="false"/>` inside `<activity>`.
- Anecdotal double delivery on Android even with the flag off ([#245](https://github.com/llfbandit/app_links/issues/245)) is another reason to keep WU3's dedupe and WU6's idempotent run handling.

Q3: package visibility. **`canLaunchUrl` needs declarations; `launchUrl` doesn't.**
- iOS: `checklister` must be listed in `LSApplicationQueriesSchemes`, or `canOpenURL` always returns false. The cap is 50 entries, or 25 for apps linked on iOS 27+, so one entry is fine ([Apple](https://developer.apple.com/documentation/uikit/uiapplication/canopenurl(_:))).
- Android 11+: url_launcher's `canLaunchUrl` uses `resolveActivity` and needs a `<queries>` `<intent>` with VIEW + `<data android:scheme="checklister"/>`, added to the existing `<queries>` block ([url_launcher README](https://github.com/flutter/packages/blob/main/packages/url_launcher/url_launcher/README.md), [declaring](https://developer.android.com/training/package-visibility/declaring)). `<package android:name="com.checklister"/>` alone is not documented to cover custom-scheme resolution, so use the intent form.
- `launchUrl` needs neither declaration ([use cases](https://developer.android.com/training/package-visibility/use-cases)). It returns false when nothing handles the URL, which WU5's could-not-open error path should rely on.

**WU1 audit catch: FK cascade + INSERT OR REPLACE (PR #466)**

- **The bug:** WU1 declared `checklist_runs.showup_id REFERENCES showups(id) ON DELETE CASCADE`. But `SqliteShowupRepository.updateShowup` writes with `ConflictAlgorithm.replace`, and with `foreign_keys = ON` a REPLACE deletes the old parent row first. That fires the cascade, so **every showup update wiped its checklist run**.
- **Who would hit it:** the note save, the status update and the Firestore pull merge all go through this write path.
- **What the user would see:** a showup locked back behind "Run checklist", or a late-finished run auto-failed.
- **Why it slipped through:**
  - The audit (opus) confirmed it in sqlite3, and the user called it a nice catch.
  - Neither the plan nor the implementer (sonnet) caught it.
  - The cascade tests only covered DELETE, never an update of the parent.
- **Caught before merge:** the parallel review loop (architecture review plus audit) on the WU's own PR found and fixed it before it reached `main`, and before WU5/6 wired in the gate that would have exposed it to users. That counts as the review loop working as intended.
- **Fix:** drop the foreign keys on the new tables and use `AFTER DELETE` triggers instead. REPLACE doesn't fire delete triggers while `recursive_triggers` is off, and existing code stays untouched, as the user asked.
- **Debrief candidates:**
  - When a plan adds a table that references an existing one, check how the parent is written (REPLACE vs UPDATE) before choosing `ON DELETE CASCADE`.
  - The migration guide could add a "parent-update survives" test alongside the delete-cascade test.
- **Process slip:** WU1's implementer wrote the production code before the tests, which is not TDD. It still delivered full coverage.
