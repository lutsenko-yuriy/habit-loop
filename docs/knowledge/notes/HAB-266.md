# HAB-266: Research: are docs/knowledge/notes/BOOKMARKS.md bookmarks proliferating faster than they're useful?

## Notes

### 2026-09-09

**Ticket's "43 entries" premise was a miscount — verified from source**

The ticket description cited "43 entries as of 2026-09-03," which is `BOOKMARKS.md`'s line count (`wc -l`), not its row count. The table actually has 29 defined bookmarks. Worth flagging since this kind of file-length-vs-row-count mixup is an easy trap for any future audit of a markdown table.

**Audit: usage distribution across 104 notes files**

29 bookmarks, 170 total note↔bookmark associations (~1.6 bookmarks/note average). 7 of 29 (24%) are used on exactly one note: `l10n-glossary`, `linear-efficiency`, `postmortem-workflow`, `multi-project-scope`, `trivial-change-scope`, `notifications`, `scenario-gate-scope`. No bookmark is unused (0 notes). No true duplicates found. One adjacent-but-distinct pair flagged for the next quarterly audit to re-check as the corpus grows: `multi-project-scope` (sub-projects sharing *one* repo) vs. `cross-project-sync` (syncing harness content across *two* separate repos) — related concepts, currently distinct enough to keep separate.

**Existing mechanism already covers this ticket's third ask**

Heavy-tier `/checkup` dimension 9, "Knowledge-corpus bookmark health" (added HAB-221 WU3), already flags unused/obsolete/redundant bookmarks on a quarterly cadence — this ticket's ask to "decide whether periodic pruning is needed" was already answered before this ticket was filed. Decided (user-confirmed): leave `/debrief` step 4's bookmark-proposal gate as-is rather than adding a pre-emptive "≥2 tickets" recurrence bar — a 24% singleton rate is unremarkable for a taxonomy still growing organically, and gating proposal at insight-capture time would delay tagging genuine first occurrences to duplicate work the quarterly checkup already does after the fact.
