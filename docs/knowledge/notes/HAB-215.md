# HAB-215: Break end date resumes same day instead of the day after

## Notes

### 2026-08-09

**Pre-existing flaky/broken scenario found while validating the fix**

`break_flow_test.dart`'s `start_break_from_tailzone_showup_defaults_to_today` fails deterministically (ran twice) on the iOS simulator — `openTimeline`'s `drag()` finder ambiguously matches 2 `ListView`s on the pact detail scroll view. Confirmed it also fails identically on unmodified `origin/main` via a throwaway worktree, so it's unrelated to this ticket's fix. Needs its own troubleshooting ticket.

**Fix moved from the view model to the domain layer after audit review**

The first pass fixed `plannedEndDate` only at write time (`PactBreakCreationViewModel.submit`, converting to an end-of-day timestamp before persisting). `audit-code` correctly flagged that this does nothing for breaks already saved before the fix ships — their `plannedEndDate` stays at midnight forever, so upgrading users would still hit the exact bug this ticket claims to fix. Moved the day-vs-instant distinction into `PactBreak.contains()`/`isResolved()`/`stop()` instead, evaluated at read time — self-heals legacy data with no migration needed. `stoppedAt` (the literal "Resume pact" tap instant) is deliberately excluded from the widening.

Also folded in two more requests that came up mid-review: a "next showup expected on…" hint on the break-creation screen (routed through a new `PactBreakService` method rather than reaching into the showup slice's repository directly — flagged in architectural review), and allowing a same-day break (previously the picker enforced a 2-day minimum).

### 2026-08-09 (2)

**Pre-existing reminder bug found during second audit pass — needs its own ticket**

`lib/slices/dashboard/ui/generic/language_picker_handler.dart:80` calls `ReminderSchedulingService.scheduleRemindersForShowups` without the `breaks:` parameter — every other call site (`dashboard_view_model.dart`, `pact_creation_view_model.dart`, `pact_edit_view_model.dart`, `pact_break_service.dart`) threads it through. Changing app language while a pact has an active break would resurrect reminders that break suppression already cancelled. Pre-existing, unrelated to HAB-215.

### 2026-08-09 (4)

**scenarios.yml dispatch caught a real regression from the hint row — HAB-199 failure class recurring**

`start_break_fixed_end_marks_inwindow_showups_onbreak` and `start_break_requires_rationale` both failed on CI with `StateError: Bad state: No element` from `WidgetController.ensureVisible` inside `_enterRationaleAndSubmit`. Root cause: the "next showup" hint row added extra height to the break-creation screen's `ListView`, pushing the submit button past the list's initially realized extent on CI's short Android emulator viewport — `ensureVisible` requires the element to already be built/mounted, which it wasn't yet. Exactly the class of bug HAB-199 (and HAB-196/HAB-211) already diagnosed and fixed elsewhere in this same file, just not at this particular call site since it had never needed it before.

Fix: switched `_enterRationaleAndSubmit` from `tester.ensureVisible(...)` to `tester.dragUntilVisible(..., find.byType(ListView), const Offset(0, -100))`, matching the established pattern (`scrollToPactDetailStartBreakButton`, `openTimeline` in `harness.dart`). Verified by launching the `API29_CI_Match` emulator locally (`flutter emulators --launch API29_CI_Match`) — reproduced the exact CI-viewport conditions, confirmed the failure, applied the fix, confirmed green twice in a row. `start_break_from_tailzone_showup_defaults_to_today` (the scenario noted as flaky on iOS above) passed cleanly on this Android run — that flakiness is iOS-simulator-specific, not present here.

**Debrief candidate**: worth flagging in `FEATURE_WORKFLOW.md` or the `implement`/`draft-scenarios` skills that any UI change adding vertical content to an existing lazy-list screen should prompt a check of nearby `ensureVisible` calls in its integration tests — this is now the third or fourth time this exact symptom (`ensureVisible` on a not-yet-built element, Android-emulator-only) has been independently rediscovered rather than checked for proactively.
