# HAB-245: Remove exclamatory opener from break-over reminder notification title

## Notes

### 2026-08-18

**Trivial-change workflow gap**

This ticket was a one-line-per-locale string edit — no logic, no new screens, no
architecture surface — yet went through the full weight of the standard workflow
(branch, PR, both review skills, Codecov gate). Worth revisiting at debrief: define a
`[trivial]` classification for changes where nothing would need doing on our side if the
project had a CMS for this kind of content (copy tweaks, icon swaps, string-resource
edits) — and only force a release for such a change when the user explicitly asks for it,
rather than always running the full ceremony.

## Debrief summary

### 2026-08-18

**What went well**
- The ticket itself: trivial, quick, smooth — exactly as expected for a one-line-per-locale copy edit.

**What was hard or surprising**
- The overhead-to-change ratio was way off — a full branch/PR/two-review-skill/Codecov cycle for a single-line string swap wasted a noticeable amount of tokens relative to the size of the change.

**What to change**
- Introduced a `[trivial]` CHANGELOG classification and fast path: ticket → change → PR → `/debrief` (review loop skipped entirely) → merge via `/ship`. A `[trivial]` entry doesn't trigger a build/release by default — it rides along with the next real release — unless the user explicitly asks for an immediate one. Documented in `docs/workflows/FEATURE.md` and `docs/VERSIONING.md`; actual CI/scripts wiring tracked separately as HAB-247 (not implemented yet — do not tag a real entry `[trivial]` until that ships, or `scripts/changelog/lint.py` will fail it).
- Also noted: working on multiple tasks at once (this ticket + HAB-246 planning in parallel) was called out as a secondary source of slowdown/overhead this session, though no concrete workflow change was proposed for it.
