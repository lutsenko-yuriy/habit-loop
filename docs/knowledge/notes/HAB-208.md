# HAB-208: Stop pact: showups wiped entirely and break banner stays after stopping

## Notes

### 2026-07-31

**PactTransactionService's atomicity boundary stops at pact_breaks**

`PactTransactionService`'s own docstring scopes it to atomic writes spanning `pacts` and `showups` only. `stopPact`'s break resolution (`PactBreakService.stopBreak`) is a separate, non-atomic write issued after `stopPactTransaction` completes. A crash between the two leaves a stopped pact with an unresolved break, but it's self-healing: the break banner's visibility and its "Resume pact" button are derived purely from the break's own `stoppedAt`/`plannedEndDate`, independent of `pact.status` — tapping it again resolves the break correctly even on an already-stopped pact. Decided to leave this as a known narrow gap rather than extending `stopPactTransaction` to cover `pact_breaks` atomically, consistent with `PactBreakService`'s own writes (`updateBreak`/sync/cache/reminders) already not being atomic with each other either. Candidate follow-up if this ever needs tightening: pass an already-computed `PactBreak.stop(now)` into `stopPactTransaction` so pact status + showup pruning + break resolution commit together.

## Debrief summary

### 2026-07-31

**What went well**
- Once investigation started, the proximate cause (`stopPactTransaction` unconditionally deleting *all* of a pact's showups instead of a status/date-scoped subset) was identified and fixed quickly.

**What was hard or surprising**
- Showups are core domain data — the whole point of the app is letting the user track their habit history through them, in stats, the timeline, and the showups themselves — yet the code that deleted every one of them on stop somehow made it into the app. The behavior wasn't there initially; it was introduced partway through development. Mitigated in practice only by luck: Firestore still held the data, and current testers know the app is pre-release. A production user wouldn't get either cushion.

**What to change**
- Wants a dedicated root-cause investigation for the original regression (when and why "delete all showups" was introduced, and why review/tests didn't catch it) rather than reconstructing it ad hoc during this debrief — to be opened as a separate Linear ticket.
- Proposed splitting bug work into two phases going forward: `TROUBLESHOOT_WORKFLOW` for pre-fix diagnosis (as today), and a new `POSTMORTEM_WORKFLOW` for post-fix root-cause analysis. Decided to trial this ad hoc within the upcoming investigation ticket first rather than write the workflow doc now — only formalize into `docs/POSTMORTEM_WORKFLOW.md` (wired into `AGENTS.md`/`TROUBLESHOOT_WORKFLOW.md`) later if it proves useful. Possibly also adopted in a related project ("Yuriys-agentic-boyz") if it does.
