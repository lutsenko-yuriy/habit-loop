### 2026-07-25

**Architectural decisions taken before planning (from the user at step 1.5)**

- **On-break is derived at read time, never stored on the showup row.** A pending showup is "on break" iff its `scheduledAt` falls inside any of its pact's break windows. No materialised field, no snapshot.
- **A break is *stopped*, not deleted** — mirroring `Pact.stop()`. Stopping writes `stoppedAt` onto the persisted break; the record is never removed. The window becomes fixed at that instant, so the read-time derivation automatically keeps already-on-break showups on-break forever (no freeze step needed). Domain vocabulary is "stop" (`PactBreak.stop()`, `stoppedAt`); the **UI action label is "Resume pact"**; analytics event is `pact_break_stopped`.
- **Feature toggle `pact_breaks_enabled` defaults to `false`** during development (deliberate deviation from the workflow's default-true convention). The default flips to `true` in the final WU (WU6), right before shipping.
- **Break records sync to Firestore** (WU1.3). Should have been surfaced at `/brief` intake but wasn't — without it a reinstall/second device loses breaks and retroactively auto-fails on-break showups. User confirmed folding it in (as its own WU to respect the LoC ceiling).

### 2026-07-26

**Collapse guard-clause chains into a single logical expression when nothing follows the checks (debrief candidate — code style).** In WU3's `PactBreakService._rescheduleRemindersAfterStop`, a `.where()` filter was written as three sequential `if (...) return false;` guards instead of one `&&`-chained boolean expression — user flagged it in review. Doing so also surfaced that one of the guards (`status != pending`) was redundant, since `BreakDerivation.isShowupOnBreak` already checks that internally. General rule going forward: guard clauses earn their keep only when there's a non-trivial body *after* the checks (per `docs/CODE_STYLE.md`'s "guard clauses first, then unindented code for the common case") — for a closure or function whose entire body *is* the boolean check (a `.where()` predicate, a plain `bool`-returning getter), a single logical expression is more direct with no performance difference either way (Dart short-circuits `&&` the same way sequential early returns do). Worth adding to `docs/CODE_STYLE.md` alongside the existing guard-clause guidance.

**Cleanup "side quests" mid-feature should default to noted/ticketed, not done inline (debrief candidate — process).** After the single-expression fix above, user asked to scan for the same pattern elsewhere; the scan found two more instances *outside* WU3's own files (`reminder_scheduling_service.dart`'s qualifying filter, and a duplicated closure across both debug pages) and they got fixed immediately, in the same PR. User's own reflection afterward: this kind of unrelated-cleanup detour is something they decide to do fairly often mid-session, and going forward they'd rather default to capturing it as a note or a Linear ticket and continuing the feature in progress — *unless* the cleanup directly impacts the feature currently being implemented. Rule of thumb to apply going forward: before fixing a discovered issue that sits outside the current ticket's own files/scope, ask (or default to) whether it should be captured for later rather than fixed inline now, rather than assuming "small and easy" is enough justification on its own.

**Token waste from debugging by trial-and-error instead of recognizing the pattern first (debrief candidate — process/efficiency).** During WU4.1's follow-up round, moving the "Take a Break" button lower on Pact Detail (grouping it with Stop Pact) broke two widget tests with a confusing symptom: `tester.allWidgets` found the button with the correct key, but `find.byKey(...)` reported zero matches. Rather than recognizing this immediately as Flutter's well-known `skipOffstage: true` default-finder behavior (content scrolled out of the test viewport is treated as "offstage" and excluded from finders unless `skipOffstage: false` is passed, or the element is scrolled into view first), several rounds of ad-hoc debug instrumentation were added and removed (printing all `Text` widgets, all `CupertinoButton` keys, exception state, widget-type sets) before landing on the actual cause. User flagged that this pattern — spending tokens/turns iteratively poking at symptoms before pausing to recognize a known class of issue — happens more broadly and "something should be done about token waste." Rule to apply going forward: when a test failure looks like "the widget verifiably exists but the finder can't see it," check for known Flutter test-framework gotchas (`skipOffstage`, `pumpAndSettle` timing out on indefinite animations, offstage/Visibility widgets) *before* reaching for print-and-inspect instrumentation — a quick mental (or doc) checklist of "widget exists but finder returns empty" causes would have resolved this in one step instead of four. Worth surfacing at debrief as a candidate for a shared troubleshooting-checklist resource (e.g. `skills/build/implement/resources/` or a widget-test gotchas note) so this class of investigation is faster and cheaper next time.

**New l10n string picked the wrong root word for RU against the glossary's own per-language table (debrief candidate — process).** WU5.1 added `showupOnBreak` ("On break") across 4 languages; the first pass used "На паузе" (pause-root) for Russian, "Pausiert" (participle) for German, and "En pause" for French. `docs/GLOSSARY.md`'s per-language canonical-terms table (line 113) pins "break" to RU **перерыв**, FR **pause**, DE **Pause** — French's "En pause" and German's "Pause" root actually matched already (and matched WU4.1's already-shipped `startBreak`/`breakUntilPactEnds` keys, which use "Pause"/"перерыв" consistently), but Russian's "На паузе" used the unrelated "пауза" loanword instead of "перерыв", breaking consistency with WU4.1's own "Сделать перерыв"/"Начать перерыв". User caught it by inspection, not by me checking the table first. Fixed to "На перерыве" (RU) and tightened DE to "In Pause" (noun form matching the glossary's "Pause" rather than the "pausiert" participle). Rule to apply going forward: before finalizing any new user-facing string for a term that already has a GLOSSARY per-language entry, diff the proposed translation against that table (and against any already-shipped keys for the same domain concept) rather than translating from the English source string in isolation — this is really the general "verify from source" habit (canonical terms are a source-of-truth file, not something to reconstruct from memory of the English string).

### WU6 (final)

**Same pre-existing flaky scenario recurred, still unrelated to this WU's diff.** `onbreak_showup_not_autofailed_by_sweep_or_late_open` failed again in the full `break_flow_test.dart` run on `emulator-5554` while validating S9; WU6's diff (`pact_list_state.dart`, `pact_list_view_model.dart`, `pacts_summary_bar.dart`, l10n, RC flag, docs) touches none of that scenario's dependencies. Third occurrence across this ticket (also seen at WU5.2) — strengthens the case for the dedicated flakiness investigation already flagged above rather than reinvestigating per-WU.

**Break filter redesigned from an exclusive lens to a plain multi-select toggle, post-review.** After the audit fixes shipped (see above), the user asked for two more changes: (1) an "On break" badge on the pact list tile, since on-break pacts read as indistinguishable from plain "Active" ones — added, reusing `showupOnBreak`'s string and `HabitLoopColors.onBreak`, matching WU5.1's showup treatment; (2) "make break filter work the same as the rest of the filters" — a direct request to drop the exclusive-lens design entirely (the same mechanism the audit had just flagged two bugs in) in favor of `breakSelected` being a fully independent, OR-combined toggle like Active/Done/Stopped: selecting it adds on-break pacts to whatever's already selected, isolating "only on-break" requires deselecting the rest first (same as isolating any other single status), and `toggleFilter`/`toggleBreakFilter` no longer touch each other's state at all. This is strictly simpler than the lens design and the two audit findings (empty-list-when-Active-deselected, ungated visibility) don't apply to it in the first place — worth remembering that a request to simplify toward "behaves like everything else" is often the more durable fix than patching an ad hoc special case.

**Deferred (follow-up ticket candidate): "on break" derivation uses `isResolved(now)`, not `isActiveAt(now)`, so a future-dated break shows as active immediately.** Flagged by the re-audit against the new list badge, but verified pre-existing and consistent app-wide, not a WU6 regression: `pact_detail_view_model.dart:75` (the banner) and `showup_detail_view_model.dart:110` (suppression) already use the identical `!isResolved(now)` predicate from WU2/WU4.1/WU5.2. `PactBreak.isActiveAt(now)` (which does check `startDate`) already exists in the domain but nothing uses it for this purpose. Since both break-creation flows (WU4.1) allow picking a future start date, a break scheduled to start next week shows its pact as "on break" / shows the banner / suppresses reminders starting the moment it's created, not on its actual start date. Worth a dedicated ticket to decide whether that's the intended product behavior (arguable either way) and, if not, switch all three call sites to `isActiveAt(now)` together rather than fixing one in isolation.

**Flipping `pact_breaks_enabled`'s default broke 3 pre-existing `showup_detail_screen_test.dart` tests (companion-bug fix, folded in per the "directly-related" carve-out).** Once the flag defaults to `true`, `ShowupDetailScreen`'s "Take a Break" entry point appears for any non-done showup — pushing "Save Note" out of the viewport for 3 tests using `_pendingFutureShowup()` (the same `skipOffstage` gotcha documented under WU4.1 above). These tests are about note-saving, not breaks, so scoped the fix to pinning `pact_breaks_enabled: false` in the file's `_overrides()` helper rather than adding scroll calls — keeps the tests deterministic and independent of a feature they don't exercise.

**The OR-combined Break filter (previous entry above) was itself still wrong — Active alone kept surfacing on-break pacts.** User caught it by walking through a truth table (A = Active chip, B = Break chip): `A & !B` should show only active-not-on-break pacts, but the OR logic (`activeFilters.contains(status) || (breakSelected && onBreak)`) matched on-break pacts via their literal `PactStatus.active` regardless of `breakSelected`. Fixed by making Break and Active mutually exclusive for on-break pacts specifically: `e.onBreak ? breakSelected : activeFilters.contains(status)` — an on-break pact's visibility is decided by `breakSelected` alone, full stop. This was the second design iteration in a row that got the Active/Break interaction wrong before landing on the actual product intent (first the exclusive-lens design, which the audit flagged; then this OR design, which the user caught with a truth table); the pattern in both cases was reasoning about the mechanism ("what's a natural way to combine two toggles?") rather than starting from the exact visibility table the product wants and deriving the mechanism from that. Worth trying the truth-table-first approach earlier next time a filter-combination question comes up.

**Habit names must avoid a due-today showup or they collide with the dashboard's todo list text (process note).** S9 seeds two active pacts with a `DailySchedule` starting before `testNow`; both generated a showup due "today," and the dashboard's todo-list tile also renders `Text(habitName)` behind the pacts panel — so `find.text('Yoga')` matched twice (todo tile + panel tile) even before the Break filter was involved, and would have kept matching after filtering too, since the todo tile is independent of the panel's own filter state. Fixed by giving both pacts a `startDate` after `testNow` so no showups (and thus no todo-list text) exist yet — cleaner than disambiguating with `.last`, since the ambiguity would have resurfaced on every subsequent assertion, not just the first one. Worth remembering for any future integration scenario that both opens the pacts panel and asserts on a habit name by plain `find.text`.

**Real-device (well, simulator) testing caught a WU4.2 bug the entire prior test suite missed: "Take a break" offered on a showup that's already permanently on break.** User's flow: start a break covering today's showup → cancel/resume it → open that showup's detail screen. The badge correctly showed "On break" (permanent per HAB-195's read-time-derivation design — a stopped break's window is fixed, not cleared), but the "Take a Break" button also showed, since `canStartBreak`'s `hasActiveBreak` check only looks at whether some break is still *unresolved*, not whether *this showup* is already covered by one (resolved or not). Confirmed the fix scope with the user via a two-option question before touching anything, since the literal wording ("autofailing showups only") was ambiguous between narrowing the whole tail-zone eligibility rule (dropping the existing "still-pending, not-yet-due" case entirely) vs. just excluding the on-break case — user picked the minimal, targeted option. Fixed in `ShowupDetailViewModel.load()`: `isOnBreak` computed once up front (shared with the pre-existing late-open auto-fail suppression check) and added as an `!isOnBreak` condition on `canStartBreak`. No existing test (unit or integration) exercised "showup on break via a since-resumed break" — added one. Folded into WU6 rather than a separate ticket since the buggy code (WU4.2) has never been reachable by real users yet — `pact_breaks_enabled` has defaulted `false` until this exact WU flips it, so shipping WU6 without this fix would put a confusing interaction in front of users on day one.

**The Active/Break truth-table fix (above) silently broke a pre-existing WU5.2 scenario (S7) — diagnosed as a real, deterministic regression, not flakiness, before touching anything.** A full-file emulator run showed `resume_pact_stops_break_future_resumes_past_stays_onbreak` failing at `waitFor(...'pact-detail-break-banner'...)`, logging `screen: showup_detail(...)` right before the timeout — i.e. it navigated to the wrong screen. Ran it in isolation (still failed, ruling out cross-test interference), then swapped just `showup_detail_view_model.dart` back to its last-committed `HEAD` version via `git show HEAD:<path> > <path>` (per the "avoid git stash" standing preference) and re-ran — still failed, ruling out the `canStartBreak` fix as the cause. Root cause: S7's pact is already on break when the test seeds it, and the truth-table fix means an on-break pact no longer renders in the pacts panel under the default Active-only filter — so `openPactDetail`'s `find.text(habitName).last` fell through to the dashboard's todo-list tile (which navigates to *showup* detail, not pact detail) instead of the now-absent panel tile. Fixed by selecting the Break chip before calling `openPactDetail` in that one test. Any future scenario that opens Pact Detail for a pact already known to be on break needs the same chip selection first — worth a mental checklist item, since `openPactDetail`'s `.last`-based lookup gives no warning when it silently degrades to the wrong target.

**Full iOS scenario run (`test_runner.dart` on iPhone 17 Simulator) before shipping WU6 flagged 2 failures, both confirmed pre-existing and unrelated.** `onbreak_showup_not_autofailed_by_sweep_or_late_open` — the same recurring flaky scenario already seen 3× on Android in this ticket, now also on iOS. `status_write_through_visible_in_timeline_same_session` (HAB-174, unrelated ticket) — already documented in `docs/knowledge/notes/HAB-187.md` as confirmed flaky under full-suite load on iOS, passing cleanly in isolation; re-verified here (passed in isolation again). ## Debrief summary

### 2026-07-28

**What went well**
- A large, multi-WU ticket (13 WUs across several days) shipped at a speed the user considers strong for its size, despite being genuinely demanding.
- Manual/real-device testing near the end caught real bugs (the `canStartBreak` on-break gap, the S7 regression) that no automated test had caught — the user expected worse and was pleasantly surprised by how few surfaced and how quickly they were diagnosed.
- The multi-WU workflow (WU0 scenarios → WU1.1–WU6, shipping after each WU) kept a large scope manageable end to end.

**What was hard or surprising**
- Mid-implementation deviations from the original plan were the main source of friction — concretely, the pact list's Break filter chip went through three design iterations (exclusive lens → OR toggle → truth-table-exclusive) before landing on the intended behavior, and manual testing surfaced a bug in already-shipped WU4.2 code (`canStartBreak`) that had been sitting invisible behind the `pact_breaks_enabled` kill-switch.
- Not process-related: the user noted external distractions kept them from being fully focused during development at points — outside anything a workflow change addresses.

**What to change**
- Model combinatorial/multi-state logic (like the Active/Break filter interaction) with a formal model — truth table, BNF, TLA+-style spec — before implementing, rather than reasoning forward from "a natural way to combine two toggles." Added as guideline 3 in `skills/shared/decision-guidelines.md`.
- Recognize known failure classes before trial-and-error debugging; maintain lightweight per-tool "known gotchas" checklists. Added as guideline 4 in `skills/shared/decision-guidelines.md`, plus a new `skills/build/implement/resources/widget-test-gotchas.md` (first checklist, for Flutter widget tests), referenced from `implement/SKILL.md`'s TDD cycle step.
- Collapse sequential guard-clause chains with nothing after them into a single `&&`-chained expression. Added a row to the guard-clause table in `docs/CODE_STYLE.md`.
