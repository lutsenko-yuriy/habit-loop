### 2026-08-01 — Plan revision: animated transitions (before WU3 started)

Spec grew during a pre-WU3 dialog: the stripe becomes a 3-slot sliding carousel (`[predecessor, current, successor]`, current non-tappable, chevron per side only if that neighbor exists), and BOTH the stripe and the main pact-detail content now animate together (~250ms) on every chain navigation — stripe slides items into new slot positions; main content does combined slide+fade, direction-aware (predecessor nav: current out right/fades out, predecessor in from left/fades in; successor nav mirrors). A second tap during an in-flight transition is a no-op (`_isAnimating` guard), not just accepted as a possible loading-state flash. Full spec now lives in the Linear ticket description's "Update — animated transitions" section; full architecture rationale in the "Plan revision" comment.

### 2026-08-01 — WU0 stubbing a still-shipping behavior leaves a real coverage gap

WU0 (PR #346, merged) replaced `pact_chain_test.dart`'s two passing push/pop nav-stack scenarios with stubs asserting the not-yet-implemented in-place-swap behavior. Between this merge and whenever WU1 lands, `main` has **zero** scenario coverage for chain-link navigation at all — the old scenarios verified real, still-shipping behavior (the push/pop model is still what's actually running in production until WU1 ships), and they're gone. If an urgent hotfix needed to go out during this window, it would ship with that regression risk unguarded.

**Why it matters:** the standard multi-WU pattern (WU0 = scenario stubs only, no driver code) works cleanly for purely *additive* features, where the old behavior keeps running and old tests keep passing alongside new stubs. It breaks down when a WU0 stub is *replacing* a scenario that verifies behavior still live in production — deleting the old test removes real coverage before the new behavior exists to be covered.

**What to change (proposed by the user, not yet applied to this ticket):** for tickets where a WU0 stub supersedes an existing passing scenario, don't delete the old scenario in WU0. Instead: (1) mark it clearly as legacy (e.g. rename with a `_legacy` suffix or move to a clearly-labeled group), keeping it running and green against the still-current production behavior; (2) only delete the legacy version in the WU that actually makes the new scenario green (here, WU1) — the same commit that retires the old behavior retires the old test for it, so coverage is continuous throughout.

### 2026-08-01 — Smoke-test before starting the review loop

Went straight from WU1's local test run into requesting the review loop, without actually running the app and clicking through the changed flow first. `flutter analyze` + `flutter test` verify correctness, not that the feature actually works end-to-end on a device — the user flagged this as something they want to be reminded of going forward.

**What to change:** before kicking off `review-architecture`/`audit-code`, smoke-test the app on a real device/emulator — confirm it compiles and boots, then exercise the specific flow the PR touched (here: opening a chained pact, tapping "Previous Pact"/"Next Pact"). Add this as an explicit step in the review-loop entry criteria (step 10's preamble in `docs/FEATURE_WORKFLOW.md`), not just something to remember ad hoc.
