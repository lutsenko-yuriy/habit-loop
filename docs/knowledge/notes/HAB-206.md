# HAB-206: In-place Previous/Next Pact navigation stripe for chained pacts

## Notes

### 2026-07-31

**Per-WU scope (from the approved plan)**

- **WU0 — scenario updates** (`[test]`). Update `integration_test/pact_chain_test.dart`'s two existing nav-stack scenarios (`chain_navigation_previous_then_next_returns_to_same_page_instance`, `chain_navigation_next_then_previous_returns_to_same_page_instance`) to assert in-place-swap semantics instead of pop/push (only one `PactDetailScreen` ever mounted, no intermediate push/pop). Add a new scenario asserting the back button exits directly to the pacts list from any point in chain navigation. Nothing green yet beyond what already passes structurally.
- **WU1 — core navigation rework**. Convert `PactDetailScreen.pactId` from an immutable constructor arg to internal mutable state (`_currentPactId`, initialized from `widget.pactId`). Rewrite `_onOpenChainLink` to swap `_currentPactId` in place (`setState` + reload + scroll-to-top) instead of pushing a new route. Remove `cameFromPactId` entirely (no longer needed — there's only ever one route). Makes WU0's scenarios green.
- **WU2 — cache-warming prefetch**. Extend `PactDetailViewModel.load()` to warm `PactDetailCache` for the predecessor/successor bundle (pact + stats + timeline + breaks) as a fire-and-forget call, so a subsequent swap is a cache hit (instant, no spinner) rather than a fresh DB round trip. Unit-tested only, no visible UI change.
- **WU3 — chevron-stripe visual restyle (final WU)**. Restyle the existing Previous/Next Pact `Row` into the chevron-stripe look (`← name` / `name →`) on both platform pages, same position/keys. Updates `docs/PRODUCT_SPEC.md`/`docs/ARCHITECTURE.md`. `[user]` tag — this is the WU where the behavior actually becomes visible/different to a real user.

**Cross-WU invariant**: "Adjust and start again" is completely untouched by this ticket — same button, same push-based wizard, same reload-on-return outcome. Only the Previous/Next *link* navigation model changes.

### 2026-08-01 — Plan revision: animated transitions (before WU3 started)

Spec grew during a pre-WU3 dialog: the stripe becomes a 3-slot sliding carousel (`[predecessor, current, successor]`, current non-tappable, chevron per side only if that neighbor exists), and BOTH the stripe and the main pact-detail content now animate together (~250ms) on every chain navigation — stripe slides items into new slot positions; main content does combined slide+fade, direction-aware (predecessor nav: current out right/fades out, predecessor in from left/fades in; successor nav mirrors). A second tap during an in-flight transition is a no-op (`_isAnimating` guard), not just accepted as a possible loading-state flash. Full spec now lives in the Linear ticket description's "Update — animated transitions" section; full architecture rationale in the "Plan revision" comment.

**Revised per-WU scope:**
- **WU0** (unchanged): `[test]` update `pact_chain_test.dart`'s 2 nav-stack scenarios to in-place-swap semantics + new back-button-exit scenario.
- **WU1**: `_currentPactId` + `_lastDirection` (toPredecessor/toSuccessor) + `_isAnimating` guard state; `_onOpenChainLink` no-ops while animating; remove `cameFromPactId`. Makes WU0 green.
- **WU2** (unchanged): cache-warming prefetch in `PactDetailViewModel.load()`. Unit-tested only, no visible change.
- **WU3** (new — was folded into the old WU3, now split out): main content slide+fade transition, 250ms ease-out, direction-aware, driven by WU1's state. Widget-tested both directions.
- **WU4** (final, `[user]`, was the old WU3): 3-slot chevron-stripe restyle + sliding-carousel animation, 250ms ease-out, updated widget keys (predecessor/current/successor slots). `PRODUCT_SPEC.md`/`ARCHITECTURE.md` updated.

**Open risk carried forward**: the stripe's carousel needing up to 4 simultaneous pacts mid-transition (one exiting, two shifting position, one entering) is real complexity — if WU4 proves too fiddly, may need to simplify (e.g. crossfade-only stripe) as a mid-implementation discovery, not pre-decided.
