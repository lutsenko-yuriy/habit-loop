# HAB-237: Research: should CI ever push commits directly to main?

## Notes

### 2026-08-17

**Scoping — MoSCoW**

Ticket-specific constraint beyond `docs/CONSTRAINTS.md`: `main` currently has zero branch
protection (`gh api repos/lutsenko-yuriy/habit-loop/branches/main/protection` → 404), and
CI's `version-tag` job already pushes a build-number-bump commit directly to `main` with
`[skip ci]` — the existing pattern in question, not hypothetical. Must: Q1 (survey direct
push vs. bot-PR precedent, cited) + Q2 (replacement for the build-number bump if direct
push should go). Should: Q3 (branch protection + bypass-rule coexistence). Won't: any
implementation.

**Q1 — thesis/antithesis research (two-branch, single synthesis)**

Thesis: "CI pushing commits directly to `main` (e.g. an automated version bump tagged
`[skip ci]`) is acceptable for narrow, low-risk, fully-automated changes."
Antithesis: "All changes to `main`, including bot-authored ones, should go through a PR —
direct push bypasses review regardless of how narrow the change is."

*Thesis evidence:* GitHub formalized `[skip ci]` as a first-class convention
([2021 changelog](https://github.blog/changelog/2021-02-08-github-actions-skip-pull-request-and-push-workflows-with-skip-ci/)).
Widely-used marketplace actions
([stefanzweifel/git-auto-commit-action](https://github.com/stefanzweifel/git-auto-commit-action),
[gh-action-bump-version](https://github.com/marketplace/actions/automated-version-bump))
exist specifically for direct-push version bumps. `semantic-release`'s ecosystem treats
push-back-to-branch as a supported mode, engineered around branch protection via scoped
GitHub Apps/deploy keys ([blog](https://gonzalohirsch.com/blog/semantic-release-and-branch-protection-rules/),
[issue #1343](https://github.com/python-semantic-release/python-semantic-release/issues/1343))
rather than avoided.

*Antithesis evidence:* GitHub's protected-branch/ruleset docs treat direct push as
something that must be explicitly granted via a bypass list — default posture is "no one
pushes directly, including bots"
([docs](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-rulesets/available-rules-for-rulesets)).
Purpose-built release-automation bots that could push directly —
[release-please](https://github.com/googleapis/release-please) — deliberately choose the
PR-gate model instead; Renovate does the same for dependency bumps. Every real
supply-chain incident found (StepSecurity's 2026 incident log, Pillar Security's
Hackerbot-Claw report) involved an attacker exploiting a credential *capable of*
direct-to-main push — one (Azure/durabletask) used `[skip ci]` specifically to dodge
detection, the exact convention `version-tag` already uses.

*Synthesis:* Neither side found a real postmortem of a legitimate, uncompromised bot's
routine commit causing harm purely from being unreviewed — the antithesis's strongest
evidence is a broader attack-surface argument (direct-push capability is one more thing
an attacker can pivot through via credential compromise), not evidence of the bot's own
logic misbehaving. Applied to this repo: `main`'s zero branch protection means the
ecosystem's usual mitigation (bypass list on an otherwise-protected branch) doesn't even
apply here — the repo is already at the antithesis's weakest point (any credential with
write access can push unreviewed) without the thesis's usual benefit (protection + an
audited, narrow bypass). This sharpens Q3 as the more consequential open question here.

**Q2 — what replaces `version-tag`'s build-number commit-back (internal precedent, no
further search needed)**

`.github/actions/resolve-version` already resolves the build number as
`max(pubspec.yaml's stored number, highest version-* git tag)` — pubspec.yaml's committed
number is already just a floor, not the source of truth; tags win once ahead. Fix: drop
the `git commit ... [skip ci] && git push` step in `version-tag`
(`.github/workflows/release.yml:364-365`) entirely, keep only `git push --tags`.
pubspec.yaml's build number goes stale/informational (harmless — already tolerated).
Bonus: tag pushes aren't gated by branch-protection "require PR" rules at all (those apply
to branch refs, not tag refs) — this sidesteps Q3's bypass-list question entirely for
`version-tag`'s own needs.

**Q3 — should branch protection be introduced?**

Yes, independent of Q2: `main` has zero protection today, meaning any write-access
credential (human or bot, compromised or not) can push unreviewed — exactly the failure
mode the antithesis's cited 2026 incidents describe. With Q2's fix removing the one
legitimate reason CI needed direct branch-push capability, protection can be turned on
with **zero bypass exceptions** — the cleanest version of what the antithesis evidence
recommends.

**Net recommendation:** enable "require PR before merge" on `main` with no exceptions;
change `version-tag` to push tags only (drop the commit-back); build numbering keeps
working unchanged since tags were already the effective source of truth. Implementation
is out of scope for this ticket — a follow-up ticket would carry it out.
