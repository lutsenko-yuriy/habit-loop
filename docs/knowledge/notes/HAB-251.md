# HAB-251: Research: developer health (vision, ergonomics, mental load) and its effect on attentiveness/thoroughness

## Notes

### 2026-09-07

**Scoping — constraints and MoSCoW**

Ticket-specific constraints beyond `docs/CONSTRAINTS.md`: the existing intervention (`nightly_block.sh`, 23:00-08:00 hard block, with a vacation-window override via `HL_NIGHTLY_BLOCK_START_HOUR`/`END_HOUR`) is already shipped — any recommendation works within or explicitly justifies replacing that config surface. No wearables/biometric tracking available — any fatigue signal has to come from something observable in-session or self-reported. This is about the user's health/attentiveness, not the agent's.

MoSCoW: **Must** — survey evidence linking eye strain/ergonomics and fatigue/mental load to error rates in code-review/authoring-like knowledge work; assess whether a fixed clock window is a reasonable fatigue proxy vs. alternatives. **Should** — survey existing tools/practices and their solo-dev adoptability. **Could** — propose a concrete lightweight alternative/complement if evidence favors one. **Won't** (this ticket) — implement any new intervention; give clinical/medical guidance.

**Survey — developer health, attentiveness, and fatigue proxies**

Topic-mode research (no thesis to adjudicate). Evidence:

| # | Sub-question | Source | Finding | Verified? |
|---|---|---|---|---|
| 1 | Eye strain | Talens-Estarelles et al. 2022, *Contact Lens & Anterior Eye* — [doi.org/10.1016/j.clae.2022.101744](https://doi.org/10.1016/j.clae.2022.101744) | 20-20-20 rule gave symptom relief at 4 weeks; 2 weeks wasn't enough for measurable binocular/dry-eye improvement, and gains faded once reminders stopped | Metadata via OpenAlex (93 citations), not full text |
| 2 | Fatigue in dev work specifically | Fritz et al. 2014, ICSE — [dl.acm.org/doi/10.1145/2568225.2568266](https://dl.acm.org/doi/10.1145/2568225.2568266) | Eye-tracking/EEG/electrodermal sensors on working developers predicted task difficulty at up to 84% accuracy, framed as stopping bugs before they're introduced | Semantic Scholar metadata only (281 citations) |
| 3 | Fatigue accumulation vs. time-of-day | Sievertsen, Gino, Piovesan 2016, PNAS — [doi.org/10.1073/pnas.1516947113](https://doi.org/10.1073/pnas.1516947113) | Test performance drops as a session/day progresses; design (randomized test-time assignment) isolates within-session fatigue from raw time-of-day | Semantic Scholar metadata (184 citations); PNAS full text blocked (403) |
| 4 | Clock-window vs. other proxies | (same paper) | No study found directly pitting a fixed clock window against session-duration or self-report as competing "stop now" triggers — flagged as a literature gap, not answered | Same caveats |
| 5 | Existing practices | OSHA workstation ergonomics guidance | Monitor height/angle, neutral posture, glare control tied to eye strain and posture risk | Snippet only, direct fetch 403'd |

Excluded: several practitioner-blog claims about PR-review-time-of-day effects (e.g. "PRs reviewed after 3pm get fewer comments") circulated in search results but couldn't be traced to a citable primary source — treated as anecdotal, not evidence.

**Conclusion:** eye-strain and dev-specific fatigue/attentiveness each have some empirical grounding (20-20-20 study; ICSE psycho-physiological study), and general cognitive-fatigue-accumulation research exists (PNAS), but nothing found treats time-of-day-as-proxy as its own validated research question — no evidence the existing clock window is *mistargeted*, just that it's unvalidated as the single best proxy.

**Trade-off evaluation against `docs/CONSTRAINTS.md`**

| Option | Fit | Risk given current constraints |
|---|---|---|
| A — Keep fixed clock window as-is | Good | Zero maintenance, reversible via toggle, already shipped. Blunt by design, not by evidence, but no evidence found that it's actively wrong either. |
| B — Replace clock window with session-duration trigger | Weak | No study compares this to time-of-day — would swap one unvalidated proxy for another, plus new state to track. |
| C — Add a self-report/checklist gate | Weak | Requires ongoing manual input every session; constraints doc flags this as unsustainable solo, and an ignorable nag undermines the point. |
| D — Add a break reminder (20-20-20-style) alongside the existing clock block | Good | Cheap, precedented (OSHA, the 20-20-20 study), addresses a *different* mechanism (eye strain) than the clock block (late-night fatigue) — complementary, not competing. Caveat: gains fade once reminders stop, so it needs to actually keep firing, not just exist once. |
| E — Do nothing further | N/A | Leaves the literature gap unaddressed but honest that no evidence justifies replacing what's shipped. |

**Decision:** A (keep) + D (add a break reminder as a complement, not a replacement) — recorded in ADR-0007. B and C rejected as distractions from the research's own findings — no evidence backs either as an improvement over A.

**Implementation-shape discussion (for the follow-up ticket, not built here):** should the break reminder fire on a cron-like timer or be checked on the next request? Decided: **next-request-triggered** (checked on `UserPromptSubmit`, mirroring the existing `nightly_block.sh`/`alert.sh` hook pattern) — a cron timer would need a separate OS-level scheduler (`launchd`), which is more moving parts and less reversible than reusing the hook infra already in place. User's own reasoning: when deep in a single long-running task with no prompts for a while, they're "most likely doing something else" anyway, so a request-triggered check isn't missing the moments that matter.

Follow-up ticket filed: HAB-268 (break/eye-strain reminder implementation).

## Debrief summary

### 2026-09-07

**What went well**
- Quick and informative, as usual — scoped, researched, evaluated trade-offs, decided (ADR-0007), filed the follow-up ticket. User approved each step with minimal back-and-forth.

**What was hard or surprising**
- User flagged a recurring feeling that these research passes can be superficial. Dug into specifics: (1) most of this run's evidence table (4/5 rows) was verified only via metadata/citation-count (Semantic Scholar, OpenAlex), not actual full-text reads — several full-text fetches hit a 403 and the subagent didn't try an alternate route before falling back; (2) the subagent ran one broad search pass rather than a distinct pass per sub-question, so breadth across this ticket's 4 explicit sub-questions was incidental rather than deliberate.

**What to change**
- Updated `skills/design/research/SKILL.md` step 3 (subagent instructions): (a) for topic mode with multiple explicit sub-questions, run a distinct search pass per sub-question instead of one broad query; (b) try an alternate route to primary text (author site, publisher's own PDF link, institutional repository) before accepting snippet/metadata-only, and call out explicitly as a shortfall — not just a per-row footnote — if more than half the final table ends up unverified beyond a snippet.
