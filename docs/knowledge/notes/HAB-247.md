# HAB-247: Wire up [trivial] CHANGELOG tag: build suppression + delayed release-notes inclusion

## Notes

### 2026-08-19

**Design conflict found before implementation started**

Read the existing `scripts/changelog/{lint,distribute,release_notes}.py` and their tests
before touching anything:

- `distribute.py`'s `should_distribute` only checks for `[user]`/`[app]` bullets — a
  `[trivial]`-only entry already gets `should_distribute() == False` for free, no code
  change needed there once `[trivial]` is a recognized tag.
- `lint.py` just needs `'trivial'` added to `KNOWN_TAGS`/`CLASSIFICATION_TAGS` — small,
  safe, mechanical.
- **The release-notes piece is not a script tweak.** `release_notes.py` only extracts
  bullets from numbered `## [X.Y.Z]` headings — it never scans `## [Unreleased]` content
  at all, and `test_release_notes.py::test_sealed_unreleased_bullets_never_appear_in_output`
  explicitly locks in that **no** bullet inside an Unreleased batch (even a `[user]`-tagged
  one) may ever surface in release notes. This is a deliberate HAB-185 invariant: Unreleased
  = internal-only, permanently invisible to "What's New".
- Per the current `ship` routing rule, a `[trivial]`-only entry (no `[user]`/`[app]`)
  would route into `## [Unreleased]` — same bucket the invariant above protects. So
  `[trivial]` bullets would be silently lost forever under the current routing, exactly
  the outcome HAB-247's ticket description says to avoid.
- For a `[trivial]` bullet to ever reach release notes later, it needs its **own numbered
  heading** (not Unreleased) so the *existing* "unbuilt newer entries accumulate into the
  next real release's notes" mechanism (documented in `docs/VERSIONING.md`'s Selective
  build section) picks it up naturally. That requires changing `ship`'s heading-routing
  rule (which tags get a numbered heading vs. Unreleased) and deciding whether a
  `[trivial]`-only numbered heading also bumps `pubspec.yaml` — real design work, not
  wiring.

**Decision (2026-08-19, end of session):** paused before implementing. Tomorrow: either
resolve the numbered-heading-without-build-trigger design question and implement all
three pieces, or explicitly scope this ticket down to just `lint.py` + `distribute.py`
(mechanical, safe) and split the release-notes piece into its own ticket.

### 2026-08-23 (plan approved)

**WU scope summary**

- **WU1** (`feature/HAB-247-WU1-tag-and-build-gate`, `[wip]`): `[trivial]` becomes a legal
  tag — `lint.py`/`distribute.py` recognize it, build gating honours it. No observable
  release-notes effect yet.
- **WU2** (`feature/HAB-247-WU2-release-notes-and-ship-routing`, final): sealed-`## [Unreleased]`-batch
  `[trivial]` bullets reach "What's New" via `heading_boundaries.py`/`release_notes.py`;
  `ship` gains `--release-now` to route a `[trivial]`-only entry to its own numbered
  heading instead of the open batch.

Resolves the 2026-08-19 design-conflict entry above via a sealed-vs-open Unreleased batch
distinction, not the "own numbered heading without a build trigger" idea floated then.

### 2026-08-24

**Audit finding on PR #403 — `_clean_bullet`/`_should_skip` dead code**

`_clean_bullet`/`_should_skip` in `release_notes.py` are dead code (defined, never called),
so neither `[user]` nor `[trivial]` bullets actually get HAB-XX/PR#/WU-reference stripping
despite the module docstring and `VERSIONING.md` claiming they do. Pre-existing (predates
HAB-247), not fixed inline — `ship/SKILL.md` now compensates by requiring `[trivial]`
bullets to be hand-written in plain language (same as `[user]`), so this doesn't bite
ship-authored entries, but a manually-written CHANGELOG entry could still leak refs. Worth
its own tech-debt ticket: either wire up `_clean_bullet`/`_should_skip` as a real
defense-in-depth pass, or delete them and stop claiming the stripping happens.

## Debrief summary

### 2026-08-24

**What went well**
- WU1/WU2 split, formal model derived at plan time, and the sealed-vs-open batch
  distinction all held up through implementation and review without rework.
- Low-effort review/audit findings (stale docstring, regex tightening, ship guidance gap)
  fixed and threaded-replied immediately rather than deferred.

**What was hard or surprising**
- The user doesn't read Python fluently, so the automated review/audit loop is their
  *only* independent check on `scripts/` changes — a different trust profile than
  Flutter/`lib/` work, where they can read the diff themselves.
- Working late (past 11pm) may have contributed to reduced attentiveness on the user's
  side during this ticket.

**What to change**
- PRs touching `scripts/` (Python) and no `lib/` files now require a plain-language
  "What this means" section in the PR body (`pr-body-template.md`).
- `review-architecture`/`audit-code` now treat borderline Python-only findings as
  reportable rather than discardable, given the user can't self-verify (`review/SKILL.md`,
  `audit/SKILL.md`).
- Added a hard-block `UserPromptSubmit` hook (`nightly_block.sh`, 23:00–08:00 local,
  disableable via `.claude/nightly_block.env`) — a personal working-hours guard, not a
  code-quality mechanism. Documented in `CLAUDE.local.md`.
- Opened a research ticket on developer health (vision, ergonomics, mental load) and its
  effect on attentiveness/thoroughness, to inform whether the block above is well-targeted.
