# HAB-198: Integration scenario asserts stale "Pending" text for an on-break showup (post-WU5.1 regression)

## Notes

<!-- Each entry: dated heading, then named observations (bold title + paragraph).
     If the ticket is reopened after this file is finalised, create HAB-XX-adjust-N.md instead of editing this file. -->

### 2026-07-27

**Misdiagnosed as flaky across three prior WUs — actually a deterministic, one-line test bug.** `break_flow_test.dart`'s `onbreak_showup_not_autofailed_by_sweep_or_late_open` was written in HAB-195 WU3, well before WU5.1 added the "On break" visual treatment for showups. WU5.1 changed `ShowupUiState.onBreak` to render `l10n.showupOnBreak` ("On break") instead of the plain `l10n.showupPending` ("Pending") label, but this WU3-era test's assertion — waiting for the literal "Pending" text — was never updated. Since an on-break showup can never show that text again, the test has been failing consistently ever since WU5.1 shipped, not intermittently. It was repeatedly written off as the known Android-emulator/iOS-simulator timing flakiness (the same class HAB-179 tracks) at WU5.2 and twice more at WU6, because that flakiness class is real and does affect other tests in the same file — the two failure modes just happened to produce visually similar `waitFor timed out` errors. The user caught it by running the scenario enough times to notice it reproduced *stably*, not intermittently, on both platforms — a distinction worth checking directly (run in isolation more than once) before writing off any "flaky-looking" integration failure as infra noise, rather than pattern-matching on the symptom alone.

**Fix:** `break_flow_test.dart:354-356` now waits for `strings.showupOnBreak` instead of `strings.showupPending` — preserves the test's original intent (confirm the showup was not auto-failed) while matching the correct, already-shipped UI text. Verified passing on both the Android emulator and the iOS simulator.

## Debrief summary

### 2026-07-27

**What went well**
- Small, well-scoped fix — root cause found from source (l10n string mapping), verified on both platforms, shipped in one pass.

**What was hard or surprising**
- The real cost wasn't the fix itself, it was the three prior WUs (HAB-195 WU5.2, WU6 ×2) where this failure surfaced and got dismissed as the known emulator/simulator timing flakiness without being re-run in isolation to check — a genuine, deterministic bug hid behind a symptom (`waitFor` timeout) that looks identical to real flakiness.

**What to change**
- Before writing off a failing integration test as "known flaky," re-run it in isolation at least once to confirm it's actually intermittent, not deterministic. Added to `docs/TROUBLESHOOT_WORKFLOW.md`'s investigation step.
