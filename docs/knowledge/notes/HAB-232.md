# HAB-232: Personalize notifications and greetings with the user's first name

(with rationale, risk notes, and file lists) is the `/plan` comment on HAB-232.

**No existing synced-settings mechanism to reuse**

The approved intent was "synced, using the existing settings mechanism". Reading the codebase showed
there is none: `LocalePreferenceService` and `OnboardingPreferenceService` are SharedPreferences-only
and local, and `FirestoreClient`/`FirestoreSyncService` know only pacts, showups, and pact breaks.
The plan resolves this by making the display name a *fourth entity inside the existing sync machinery*
(SQLite row with `dirty`/`synced_at` + `/users/{uid}/profile/main`) rather than inventing a parallel
sync path — no new repository pattern, but genuinely new surface in five sync files. Worth re-checking
at debrief whether WU1+WU2 should have been one WU.

**Cross-device sync only really works for signed-in users**

Most users are anonymous, and `clearStaleKeychainIfFirstLaunch` mints a fresh anonymous UID on
reinstall, so the Firestore half of the "synced" decision only delivers carry-over for Google-signed-in
users. The ticket's "pre-fill from a previous install that wasn't fully wiped" case is served by the
SQLite row surviving in the app data directory, not by Firestore. User accepted this caveat explicitly
at plan approval.

**The ticket's "todo-list header" does not exist yet**

HAB-232 says the dashboard's todo-list header should be personalized, but `DashboardBody` goes straight
from the calendar strip to the showup list — there is no header today. WU6 therefore *adds* a new UI
element rather than editing existing copy. Flagged at planning and accepted by the user; note it if the
WU6 diff comes in larger than the ~170 LoC estimate.

**Two flags are needed for first-launch gating, and neither is a "skipped" flag**

`showEnterName = !isOnboardingPassed && !isNameEntryShown && flag`. `isOnboardingPassed` alone re-prompts
a user who skips and then kills the app before the dashboard renders; the new `isNameEntryShown` key alone
defaults `false` for existing users and would wrongly prompt them. A skip leaves the name null —
indistinguishable from never having been asked, per the approved intent. `firstLaunchHandledKey`
(`first_launch_auth_fix.dart`) was considered and rejected: it is written unconditionally during the first
session for the unrelated stale-Keychain concern.
