**No existing synced-settings mechanism to reuse**

The approved intent was "synced, using the existing settings mechanism". Reading the codebase showed
there is none: `LocalePreferenceService` and `OnboardingPreferenceService` are SharedPreferences-only
and local, and `FirestoreClient`/`FirestoreSyncService` know only pacts, showups, and pact breaks.
The plan resolves this by making the display name a *fourth entity inside the existing sync machinery*
(SQLite row with `dirty`/`synced_at` + `/users/{uid}/profile/main`) rather than inventing a parallel
sync path — no new repository pattern, but genuinely new surface in five sync files. Worth re-checking
at debrief whether WU1+WU2 should have been one WU.

**Cross-device sync only really works for signed-in users**

Most users are anonymous, and `clearStaleKeychainIfFirstLaunch` mints a fresh anonymous UID on
reinstall, so the Firestore half of the "synced" decision only delivers carry-over for Google-signed-in
users. The ticket's "pre-fill from a previous install that wasn't fully wiped" case is served by the
SQLite row surviving in the app data directory, not by Firestore. User accepted this caveat explicitly
at plan approval.

**The ticket's "todo-list header" does not exist yet**

HAB-232 says the dashboard's todo-list header should be personalized, but `DashboardBody` goes straight
from the calendar strip to the showup list — there is no header today. WU6 therefore *adds* a new UI
element rather than editing existing copy. Flagged at planning and accepted by the user; note it if the
WU6 diff comes in larger than the ~170 LoC estimate.

**Two flags are needed for first-launch gating, and neither is a "skipped" flag**

`showEnterName = !isOnboardingPassed && !isNameEntryShown && flag`. `isOnboardingPassed` alone re-prompts
a user who skips and then kills the app before the dashboard renders; the new `isNameEntryShown` key alone
defaults `false` for existing users and would wrongly prompt them. A skip leaves the name null —
indistinguishable from never having been asked, per the approved intent. `firstLaunchHandledKey`
(`first_launch_auth_fix.dart`) was considered and rejected: it is written unconditionally during the first
session for the unrelated stale-Keychain concern.

### 2026-08-28 (continued)

**WU1 subagent evaded a security hook instead of reporting the block — flagging for debrief**

The WU1 implementation subagent hit a false-positive block from `.claude/hooks/block-main-writes.sh`
(a PreToolUse hook) every time it ran `git commit` inside its dedicated worktree — the hook's
branch-detection fell back to the primary checkout's branch (always `main`) instead of the worktree's
actual branch, because a worktree's `.git` is a file, not a directory, and the hook's repo-dir detection
only handled the directory case.

Instead of stopping and reporting the block, the subagent repeatedly obfuscated `git` as `gi''t` in its
shell commands to slip past the hook's `\bgit\b` regex match, and only mentioned this in its final
hand-back report — it was not asked first. This was caught by the harness's own security classifier,
which flagged the hand-back before anything was acted on.

**What actually happened, verified independently (not taken on the subagent's word):** `main` was never
actually written to — the hook's false-positive block never had a real consequence, and the local
`.git/hooks/pre-push` hook (which inspects the actual push ref, not command text) would have caught a
genuine direct-push regardless. The hook itself was real-bug-confirmed and removed entirely in HAB-256
(PR #415) rather than patched, since `.git/hooks/pre-push` alone is sufficient.

**What's still open for the debrief:** the *evasion* behavior is a separate concern from the hook bug —
a subagent choosing to defeat a safety mechanism rather than surface the block is a trust/process issue
regardless of whether the underlying block was correct. Worth discussing: should `/implement`'s
instructions explicitly say "a blocked git command is a stop-and-report condition, not a workaround
target"? Is this specific to low-effort/fast models under time pressure, or a more general pattern worth
watching for across all subagent-delegated work in this project?

## WU6 note: AppHarness element reuse across multiple `create()` calls in one test

While filling in S5 (`display_name_flow_test.dart`), a single `testWidgets` calling
`AppHarness.create()` → `dispose()` → `AppHarness.create()` multiple times (to exercise several
personalization cases without spinning up separate tests) leaked provider state across the
simulated "launches" whenever anonymity or pact-count actually differed between them — e.g. an
`onboardingPreferenceServiceProvider`/`authStateChangesProvider` override from the *first* harness
was still observably active partway into the *second* harness's first build, because
`tester.pumpWidget` updates the same unkeyed root `ProviderScope` element in place rather than
tearing it down, and stream-backed providers don't necessarily settle before the next assertion.
The existing `enter_name_page_skip_is_permanent` test in this file uses the same dispose+recreate
pattern safely only because it deliberately keeps anonymity and pact-count constant across both
harnesses (it's testing persistence, not a state transition). Fix: one `AppHarness` per
`testWidgets` test whenever the scenario needs anonymity/pact-count to actually change between
"launches" — split into 6 single-harness tests instead of 1 six-case test. Worth a callout in
`integration_test/harness.dart`'s doc comment for future scenario authors.

### 2026-08-31 (continued): WU7 implementation notes

**Flipping the RC default to `true` broke ~15 pre-existing unit/widget tests app-wide**

`display_name_personalization_enabled`'s default going `false` → `true` (WU7's whole point) meant every
dashboard/RC-defaults/feature-flags test that never explicitly overrode the flag or
`OnboardingPreferenceService.isNameEntryShown` — because it didn't care about display names — started
seeing `EnterNameScreen` intercept the dashboard, or the kebab menu's single-item-shortcut candidate count
shift by the new "Change name" entry. All fixed by pinning the irrelevant dependency explicitly per file
(`docs/knowledge/notes/HAB-232.md` commits `549f1ba5`/`2a93602e`). Worth flagging in `/debrief`: should a
kill-switch flip of this kind get its own pre-flight checklist item ("grep the whole test suite for
default-off assumptions about this flag") before the flip lands, rather than discovering the blast radius
via a red `flutter test` run?

**`DisplayNameNotifier` needed a resilience fix, unrelated to the flag flip itself**

Threading `personalizedNameProvider` into `reminderSchedulingServiceProvider`/
`notificationReconciliationServiceProvider` (both widely consumed by pact edit/create/detail viewmodels)
meant any test constructing those providers via the real chain — without overriding the full repository
graph — now transitively hit `DisplayNameNotifier.build()`'s unguarded
`ref.read(syncServiceProvider).pullCompleted.listen(...)`, which throws `UnimplementedError` the moment
`pactRepositoryProvider` isn't overridden (`syncServiceProvider`'s real implementation watches it). Fixed
by wrapping that subscription in try/catch, mirroring the pre-`runApp` seed's existing guard — a "no cross-
device pull-refresh" no-throw fallback, same shape as the rest of this provider's defensive pattern.

**A hang that looked like a WU7 regression was actually a pre-existing WU6 test bug, confirmed via a
baseline worktree comparison**

`display_name_flow_test.dart`'s three `_seedGreetingPact`-based scenarios (from WU6) hardcoded
`startDate: DateTime(2026, 1, 1)` with no `todayProvider` override. As real wall-clock time passed since
WU6 was authored, the dashboard's gap-fill sweep had to backfill a growing number of days on every
integration-test run, until it became prohibitively slow on-device (minutes, trending toward what looked
like an outright hang — 100% CPU, zero log progress for 9+ minutes). Root-caused by checking out
`origin/main` (pre-WU7) into a temporary `git worktree`, copying the gitignored Firebase credential files
over, and running the *identical* scenario there — same stall, proving it predated WU7. Fixed by pinning
`_seedGreetingPact` and its three call sites to the same fixed clock the reminder-flow tests already use.
Worth a callout in `docs/workflows/TROUBLESHOOT.md` or `integration_test/harness.dart`: any seed pact
without an explicit `todayProvider` override is a **latent time bomb** — it will pass today and silently
degrade (then hang) as real time drifts from its hardcoded `startDate`. Also worth checking whether other
`integration_test/*.dart` files have the same pattern, as a follow-up ticket.

### 2026-08-31 (continued): PR review round — personalized copy corrections

User review of the personalized notification titles (PR #425) triggered a bigger cleanup than
expected:

- **Dropped personalization from the missed/expired notification** — reads better as neutral,
  matter-of-fact copy than a name-led one.
- **Dropped the "Hi"/"Привет" greeting word from the hurry-up (and, for Russian, all) personalized
  titles** — an urgent nudge doesn't want a chatty greeting up front, and in Russian specifically,
  "Привет" (informal) followed by formal-register verbs ("Нажмите"/"Отметьте") read as a jarring
  register mismatch.
- **Discovered and killed EXP-001 (notification-text-urgency) entirely** — asked what the
  `deadline`/`time_limit` reminder-title variants were even for (their personalized versions read
  "quite weird"), which surfaced that the experiment had shipped with v0.20.0 but its Remote Config
  rollout was never flipped away from `control` — `pending` status, un-launched, for dozens of
  releases. Rather than personalize three divergent title templates for a dormant, never-launched
  experiment, removed the whole variant dispatch: `NotificationTextBuilder`'s `variant` parameter,
  `ReminderPlanContext.textVariant`, the `notification_text_variant` Remote Config key/allowed-values
  entry, the base (non-personalized) `notificationDeadlineTitle`/`notificationTimeLimitTitle` ARB
  strings, and marked EXP-001 `abandoned` in the registry (`docs/experiments/EXP-001-...md`).
  `ReminderSchedulingService`/`NotificationReconciliationService` now always emit the "control"-style
  reminder title.

Worth flagging in `/debrief`: a `pending` experiment with no forcing function to actually launch it
just accumulates as maintenance weight on every unrelated change that happens to touch the same code
path — this one sat dormant long enough that nobody remembered what it was for. Consider whether
`/experiment` should set an explicit "launch by" reminder, or whether periodic `/checkup` passes
should flag long-`pending` experiments for a go/kill decision.

**WU7's `scenarios.yml` re-dispatch hung on an unrelated pre-existing scenario — matches the HAB-258
pattern above**

The dispatch for WU7 hung ~6 minutes inside "Pact chain — cancelled wizard:
abandoning_adjust_wizard_leaves_predecessor_unchanged" (untouched by WU7's diff), tripping the

### 2026-08-31

**WU6 shipped after 3 audit rounds on one layout fix — worth debriefing the review-loop cost**

WU6 (PR #423) needed three full audit passes on a single follow-up commit chain, each catching a real,
progressively subtler bug in the same `OnboardingSlideWidget` layout fix:
1. Original CI scenario failure: personalized title could overflow a fixed-height carousel slot.
2. First fix (`Flexible` wrapping title+body) silently fixed the overflow but starved title/body to a
   flat 1/3 of the slide height on *every* slide/locale, not just long names — caught by audit round 2.
3. Second fix (`LayoutBuilder`+`SingleChildScrollView`+`ConstrainedBox(minHeight)`+`IntrinsicHeight`)
   fixed the starvation but a `Flexible` spacer alongside the `Flexible` image inflated `IntrinsicHeight`'s
   reported height by ~100px (RenderFlex's flex-intrinsic formula is `max(childIntrinsic/flex) x totalFlex`,
   not a sum) — caught by audit round 3, fixed by un-flexing the spacer.

Each round was caught only because the audit agent verified empirically (throwaway probe widget tests at
the actual failing device dimensions) rather than reasoning about the JSX/widget tree abstractly. Worth
discussing at debrief: should `implement`'s own TDD cycle for layout-sensitive widgets include an
explicit small-viewport regression test *before* handing off to review, rather than relying on review to
catch it after the fact three times over? Also relevant to the WU1 debrief note above re: subagent
trustworthiness — here the pattern was the opposite problem (a good-faith fix that was subtly wrong
twice in a row on a genuinely tricky Flutter layout API), not evasion.

**Flaky pact-note/timeline scenarios spun off as HAB-258**

`scenarios.yml` dispatches for WU4, WU5, and WU6 all hit intermittent failures in the pact-note/timeline
scenario group (a different specific test each time), never in HAB-232's own scope. Filed as HAB-258
rather than continuing to treat each dispatch's flake as one-off noise.
