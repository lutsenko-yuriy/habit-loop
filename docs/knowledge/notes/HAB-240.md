# HAB-240: Research — organize multiple tickets into a shared release, for solo dev and small-team scale

## Notes

### 2026-08-17 — Scoping survey: release batching for solo/AI-agent and small-team scale

Ticket-specific scoping (per `docs/workflows/RESEARCH.md` step 1), before survey:

- **Constraints beyond `docs/CONSTRAINTS.md`**: the app already ships multiple times a day
  with no app-store review gate — a real velocity advantage that release batching would
  work against. `ship`/`FEATURE.md` currently bake in a strict 1-ticket → 1-PR →
  1-(possible)-release mapping. HAB-185's `## [Unreleased]` CHANGELOG batching already
  exists, but only for internal-only entries — not a general release-batching mechanism.
- **MoSCoW of the ticket's 4 research questions**: Must = Q1 (does batching beat the
  current per-PR model for solo+agent) and Q3 (what would concretely change in
  `docs/VERSIONING.md`); Should = Q4 (Linear Milestone/Project/Cycle vs. a lighter
  convention — only matters once Q1/Q3 say "yes, batch"); Could = Q2 (hypothetical ≤6-dev
  team — may already be answered by whatever Q1/Q3 conclude); Won't = implementation
  (explicitly out of scope).
- **Internal precedent (HAB-6/HAB-7)**: both were stock Linear onboarding-template
  issues ("Use Cycles…", "Use Projects…"), never started, bulk-canceled the same day
  (2024-12-17) alongside other template issues. Confirms the ticket's suspicion — no real
  evaluation happened, so no internal signal either way.

**Findings:**
- DORA: small batch size is an empirically-validated predictor of delivery and
  organizational performance; batching before release delays defect feedback and widens
  blast radius. DORA frames small batches explicitly as a "safety net for AI adoption" —
  directly relevant to this project's agent-assisted workflow. Strongest source in the
  table; argues against batching.
- GitLab release trains solve "commit transit time" — a long, serialized per-release
  QA/build cycle causing commits merged minutes apart to ship hours apart. This project's
  pipeline (CI → build → distribute, ~10-20 min, no human QA gate, no store review) has
  none of that serialization cost — the problem release trains solve doesn't exist here.
- Jonathan Hall's solo-dev guidance splits by artifact type: server apps → continuous
  auto-deploy per merge; installed/packaged apps → buildable-on-demand rather than forced
  auto-push. This app is mobile (installed-app category) but its actual distribution
  behavior (Firebase/TestFlight, no store review, multiple pushes/day) matches the server
  case in practice — undermines an assumption that "mobile app" alone implies batching.

**Explicit gaps** (not answered by this survey): no verified source on release-train
cadence for any specific reference project (e.g. Chrome); no source — verified or
snippet — describing solo/indie developers deliberately batching tickets into shared
releases as documented practice; no source quantifying micro-release downside (changelog
noise, version churn) at small scale. Q2 (≤6-dev team precedent) and Q4 are effectively
unanswered by this session.

**Net read on the Musts (Q1/Q3)**: the evidence that does exist leans toward "the current
per-PR model already matches best practice for this project's actual constraints" — no
source supports batching, and the strongest source (DORA) argues the opposite.

### 2026-08-18 — Closing Q2 and Q3

**Q2 (≤6-dev team precedent):** `docs/CONSTRAINTS.md` fixes this project at solo-dev +
pre-public-launch, and explicitly says to defer infrastructure that only pays off at a
scale not yet reached. Q1's per-PR-model finding already holds at the current scale, so
a hypothetical ≤6-dev evaluation adds no decision-relevant information today — it was
marked Could-have in the MoSCoW pass precisely because it's contingent on Q1/Q3 saying
"batch," which they don't. Leaving unanswered by design; revisit only if team size
actually changes (the constraints doc's own reversibility principle).

**Q3 (concrete `docs/VERSIONING.md` changes, if batching were pursued anyway):** answered
hypothetically, since the Must conclusion is not to adopt it. If forced: HAB-185's
`## [Unreleased]` batching (currently scoped to internal-only entries) would need to
extend to `[user]`/`[app]` entries too, plus an explicit "cut a release" trigger step
(manual command or schedule) to replace the current implicit trigger (any app-changing
merge to `main`). That shifts version-bump timing from "next qualifying PR" to "next
scheduled batch" — trading away the fast-feedback cadence `docs/CONSTRAINTS.md` already
flags as a real advantage at this stage, for no offsetting benefit identified in the
survey.

**Conclusion:** keep the current per-PR/per-ticket release model as-is. No
`docs/VERSIONING.md` changes. Recorded as ADR-0005.

**Resolved** — all four research questions addressed; ready to debrief.
