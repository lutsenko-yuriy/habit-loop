# HAB-246: Hurry-up reminder before a showup's window closes

## Notes

### 2026-08-19 — Research-WU findings

**Question 1: does `flutter_local_notifications` (pinned `19.5.0`, `pubspec.lock`) accept
negative notification IDs on both platforms?** Yes, confirmed by reading the plugin
source directly in `~/.pub-cache/hosted/pub.dev/flutter_local_notifications-19.5.0/`:

- **Android** (`FlutterLocalNotificationsPlugin.java:2109`): `int id = (int) arguments.get("id");`
  — a plain Java `int`, passed straight through to `NotificationManager`/`AlarmManager`
  APIs that take `int`. No positive-only validation anywhere in the plugin's Java source
  (`grep` for `id > 0` / `id >= 0` / "positive" returned nothing).
- **iOS** (`FlutterLocalNotificationsPlugin.m:558-560`, `getIdentifier:`):
  `return [arguments[ID] stringValue];` — the same method backs both scheduling and
  `cancel:` (line 597-602 calls `[id stringValue]` too), so schedule and cancel derive
  the identical string identifier from the same `NSNumber`. `NSNumber.stringValue` for a
  negative integer produces a normal string (e.g. `"-1073741824"`); `UNNotificationRequest`
  identifiers are arbitrary strings with no digit-only or sign constraint.

**Conclusion: the plan's negative-range formula
(`hurryUpNotificationId = -((_fnv1a32(showupId) % 0x40000000) + 1)`, range
`[-0x40000000, -1]`) is safe on both platforms.** No fallback to re-partitioning positive
ranges is needed — WU1 can proceed as planned with the negative range.

**Question 2: iOS 64-pending-notification cap.** Already cited in the plan comment via
three independent Apple DTS engineer confirmations on the Apple Developer Forums
(threads [811171](https://developer.apple.com/forums/thread/811171),
[765490](https://developer.apple.com/forums/thread/765490),
[682509](https://developer.apple.com/forums/thread/682509)) — no new source needed here,
existing citations stand. No equivalent hard cap exists on Android.

**Decision: Research-WU is complete, unblocked.** Proceed to the Checklist-WU and WU1.

**WU3 audit finding (PR #399), deferred to WU4:** `DashboardViewModel._runGapFillSweepAndScheduleReminders`
passes `now: todayNorm` (midnight) to `scheduleRemindersForShowups`, and its `futureShowups`
bucket deliberately includes same-day showups whose actual clock time has already passed
today. For the reminder/deadline paths this is pre-existing, tolerated imprecision — no
guard exists there. For hurry-up specifically, WU2's transport-layer guard
(`if (!fireAt.isAfter(DateTime.now())) return;`) silently drops these at the real clock,
while `ReminderSchedulingService`'s own `hurryUpCount`/`scheduledCount` still increment
(computed against `effectiveNow`, not real time) — inflating `hurry_up_count` on the
dashboard-refresh path specifically, the app's most-exercised call site and the exact
metric WU4's rollout will be judged on.

Not fixed in WU3: a real-clock comparison inside `ReminderSchedulingService` would break
every test's fixed-date determinism (the injectable `now` param exists precisely to avoid
`DateTime.now()` in this service), and changing `DashboardViewModel`'s `now:` argument is a
call-site decision with blast radius beyond hurry-up alone. Revisit before WU4 flips
`hurry_up_notification_enabled` to `true` — options: accept the imprecision (it only
affects a metric, not delivery — the transport guard already prevents any bad
notification), or thread a second real-clock check through specifically for the hurry-up
counter.

### 2026-08-23 — WU4: deferred audit findings, final disposition

**`hurry_up_count` metric inflation (above): accepted as-is.** No code change. The
transport-layer guard (`if (!fireAt.isAfter(DateTime.now())) return;`, WU2) already
prevents any bad notification from firing — this is purely an analytics-count precision
gap on the dashboard-refresh call path, bounded to at most one stale count per pact per
refresh (the same-day-past slice `todayNorm` can misclassify). Not worth threading a
second real-clock parameter through a service whose entire test suite is built on
injectable-`now` determinism, for a metric-only discrepancy.

**Android's uncapped per-showup notification count: accepted, not a WU3/WU4 regression.**
Android has never had a pending-notification cap (unlike iOS's OS-enforced 64), so adding
a third notification per eligible showup is a scaling change already inherent to Android's
existing reminder+deadline pair, not something introduced by the hurry-up feature. No
action taken.

Both were re-confirmed at WU4 flag-flip time (`hurry_up_notification_enabled` → `true`,
PR for WU4) and no new information changed the WU3 disposition.
