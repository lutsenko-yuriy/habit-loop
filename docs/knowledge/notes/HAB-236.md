# HAB-236: Research: reading Markdown reports/PRs on GitHub — fonts/colors, doc structure, delivery surface

## Notes

### 2026-08-17

**Scope extension: same preference applies to Claude Code CLI, not just GitHub**

User wants to know whether any Markdown-readability improvement found for GitHub viewing (Q1)
also has an equivalent applicable to the Claude Code CLI terminal output — same underlying
"easier to read" preference, two separate rendering surfaces (GitHub web vs. terminal).
Fold into Q1's survey; not a scope change to the ticket's Must/Should/Could split.

**Q1/Q3 research findings (topic-mode, single subagent, single synthesis)**

- **Q1 GitHub styling:** No user-level font/line-height setting for rendered markdown body
  text exists on GitHub (only the editor's monospace-vs-proportional toggle). The
  `.markdown-body` CSS class is externally overridable (confirmed via
  [sindresorhus/github-markdown-css](https://github.com/sindresorhus/github-markdown-css)),
  so a personal Stylus/Tampermonkey userstyle is mechanically viable, but no ready-made,
  maintained one targeting a Claude/Medium/TeX look was found — DIY only.
- **Q1-extension, Claude Code CLI:** `/theme` ([docs](https://code.claude.com/docs/en/terminal-config))
  is color-only (ANSI/RGB tokens), no font/line-height concept (terminals don't expose
  that). More importantly the CLI's own markdown renderer drops ~40% of GFM semantics
  (header hierarchy, link labels, strikethrough, checkboxes —
  [anthropics/claude-code#26390](https://github.com/anthropics/claude-code/issues/26390),
  closed not-planned; open ask:
  [#13600](https://github.com/anthropics/claude-code/issues/13600)). No settings exist to
  fix this — upstream product gap, outside this project's control.
- **Q3 delivery surface:** Direct precedent exists —
  [bbc/morty-docs](https://github.com/bbc/morty-docs), a static site built specifically to
  publish GitHub-stored postmortem markdown more readably. General static-site tooling
  (Docusaurus/MkDocs/GitBook) trades readability for build-pipeline maintenance; sources
  recommend lighter tooling or none at solo/small scale. No precedent found for a
  Claude-Artifact-style rendered page as an alternative — unaddressed territory.
- **Q4 navigation aids:** GitHub auto-generates a TOC for any `.md` file with 2+ headings
  ([2021 changelog](https://github.blog/changelog/2021-04-13-table-of-contents-support-in-markdown-files/)),
  and native `<details>`/`<summary>` collapsible sections work today, zero tooling, no
  source restructuring beyond adding headings/wrapping content.

**Q2 finding: no restructuring needed (internal precedent, no `/research` invoked)**

HAB-169 already settled directory-level organisation (`notes/` vs `decisions/` vs
`experiments/`, one-file-per-ticket). Current file sizes confirm nothing is actually
bloated by content-type mixing: ticket notes files top out ~115 lines (HAB-202), and
`docs/*.md` reference files are all reasonably bounded (largest non-append-only one is
`ARCHITECTURE.md` at 200 lines). `CHANGELOG.md` is large (2796 lines) but append-only,
queried by section, not read start-to-finish — expected by design. Conclusion: the
"wall of text" complaint isn't a file-organisation problem — HAB-169 already fixed that
layer. What remains is a within-file navigation problem, already answered by Q4
(GitHub's auto-TOC, `<details>` collapsibles). Splitting a note file by content type
would re-fragment what HAB-169 deliberately consolidated, for no size benefit at
current file lengths.

**Overall ticket conclusion:** research-only, no standing decision crystallized that
warrants an ADR — no implementation was in scope. Findings above (Q1 DIY userstyle
path + no CLI equivalent, Q3 no artifact precedent found, Q4 concrete zero-tooling
wins) are available for a future ticket to act on if desired.
