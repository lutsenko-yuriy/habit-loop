# HAB-211: 5 scenarios failing on every main-push CI run since HAB-202 WU4

## Notes

### 2026-08-01

**Long-running local emulator test runs need a health-check/timeout, not just "wait for notification"**

While reproducing this ticket's failures on the local `API29_CI_Match` emulator, a `flutter test integration_test/test_runner.dart` run hung for 45+ minutes with zero progress past `(setUpAll)` — no crash, no timeout, no output, just silent. It only surfaced because the user noticed and asked "it looks stuck"; nothing on my side detected it. The kill only happened as a side effect of an unrelated `adb devices -l` call restarting the adb daemon.

**Why it matters:** relying purely on "background task will notify me when done" breaks down when the process itself wedges rather than exiting — there's no natural completion event to wait for, so the session (and the user) just sits there indefinitely with no signal something is wrong.

**What to change:** for long-running local device/emulator commands (test runs, app installs, anything talking to a real or virtual device), either poll for forward progress with a sanity timeout (e.g. no new output for N minutes → treat as stuck, kill and retry/report) rather than an unbounded wait, or set an explicit `timeout` on the Bash call sized to something a bit past the expected duration so a hang surfaces as a clear failure instead of silence.

**A fixed pump count after `enterText` is not reliable on CI — poll instead**

`existing_stop_reason_prepopulated_and_editable` asserted the save button was enabled immediately after `enterText` + a fixed number of `pump()` calls. One extra pump made it pass on one CI dispatch and fail identically on the next — genuine frame-count flakiness in how long the `ValueListenableBuilder` rebuild takes on CI's emulator, not a number that could be hard-coded correctly. Replaced with a bounded poll loop (same shape as the existing `waitFor` helper, but for a boolean condition instead of a `Finder`). Two consecutive clean CI dispatches confirmed the fix.

**Why it matters:** any assertion that reads UI state derived from a listener/provider rebuild right after a user-input action (not just scrolling, which this ticket's other fixes covered) is at risk of the same flakiness on CI's slower/different-arch emulator. A fixed pump count is a guess at how many frames a rebuild takes; a poll-with-timeout is correct regardless.

**What to change:** if `harness.dart` grows more of these input→immediate-assertion patterns, consider promoting a generic `waitForCondition(tester, bool Function())` helper (parallel to `waitFor(tester, Finder)`) instead of solving each occurrence ad hoc.
