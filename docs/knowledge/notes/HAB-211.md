# HAB-211: 5 scenarios failing on every main-push CI run since HAB-202 WU4

## Notes

### 2026-08-01

**Long-running local emulator test runs need a health-check/timeout, not just "wait for notification"**

While reproducing this ticket's failures on the local `API29_CI_Match` emulator, a `flutter test integration_test/test_runner.dart` run hung for 45+ minutes with zero progress past `(setUpAll)` — no crash, no timeout, no output, just silent. It only surfaced because the user noticed and asked "it looks stuck"; nothing on my side detected it. The kill only happened as a side effect of an unrelated `adb devices -l` call restarting the adb daemon.

**Why it matters:** relying purely on "background task will notify me when done" breaks down when the process itself wedges rather than exiting — there's no natural completion event to wait for, so the session (and the user) just sits there indefinitely with no signal something is wrong.

**What to change:** for long-running local device/emulator commands (test runs, app installs, anything talking to a real or virtual device), either poll for forward progress with a sanity timeout (e.g. no new output for N minutes → treat as stuck, kill and retry/report) rather than an unbounded wait, or set an explicit `timeout` on the Bash call sized to something a bit past the expected duration so a hang surfaces as a clear failure instead of silence.

**A fixed pump count after `enterText` is not reliable on CI — and the race is systemic, not one assertion**

`existing_stop_reason_prepopulated_and_editable` asserted the save button was enabled immediately after `enterText` + a fixed number of `pump()` calls. One extra pump made it pass on one CI dispatch and fail identically on the next. A single poll-with-timeout fix for that one assertion then passed twice — but the *next* dispatch after that failed a *different* test in the same file (`clearing_note_saves_empty_value`), which had no wait at all before tapping Save: it just silently tapped a disabled button (a no-op) and the persisted value came back unchanged. Same underlying race (an `enterText`-driven `ValueListenableBuilder` rebuild that intermittently takes anywhere from one frame to several seconds on CI's emulator), surfacing at a different one of the file's four `enterText` call sites each time depending on which test happened to run when the timing was unlucky. Fixed by consolidating all four sites into one `_enterNoteText` helper that always polls for the button to reflect the change before returning, instead of trusting a single `pump()` at three of the four sites. Two consecutive clean CI dispatches confirmed the fix (a third dispatch in between failed for an unrelated reason — the CI emulator itself failed to boot, `adb: could not connect to TCP port 5554` — not a test failure).

**Why it matters:** a flake that "looks fixed" after passing on the assertion you were watching can just be the same race relocating to a sibling call site with weaker or no guard. Don't declare a race-condition fix confirmed from one passing dispatch when the fix only covers the specific assertion that happened to fail last — audit every call site with the same shape (here: every `enterText` on the same field) before considering it closed.

**What to change:** if `harness.dart` grows more of these input→immediate-assertion patterns outside this file, consider promoting a generic `waitForCondition(tester, bool Function())` helper (parallel to `waitFor(tester, Finder)`) instead of solving each occurrence ad hoc.
