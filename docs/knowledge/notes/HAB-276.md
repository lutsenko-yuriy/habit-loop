# HAB-276: Research: strategy for syncing YAB template updates into an already-adopted project

## Notes

### 2026-09-16

**Research-WU: survey of scaffold/template update-propagation precedent**

Topic-mode `/research`, one subagent, five distinct sub-question search passes (git
subtree/submodule, Copier, cookiecutter+cruft, Yeoman, framework-native update tasks). Full
evidence table posted to the Linear ticket comment; synthesis below.

Five patterns surveyed, ranked most → least automated:

1. **Copier's `copier update`** — strongest precedent. An "answers file" records the template
   version + parameters used to generate the project. On update: regenerate a fresh copy at the
   old recorded version, regenerate again at the new version, diff those two clean regenerations,
   apply that diff onto the actual diverged project via a 3-way merge. Conflicts get inline
   `<<<<<<<` markers or a `.rej` patch file for manual review. A community tool
   (`copier-update-action`) layers an AST-aware merge driver on top because plain text 3-way merge
   often isn't enough. [docs](https://copier.readthedocs.io/en/stable/updating/).
2. **cruft** (bolt-on for cookiecutter, which has no native update path) — stores `.cruft.json`
   with the template commit hash used at generation; `cruft diff`/`cruft update` diff current
   template HEAD against that hash and apply. Divergence handled via an explicit **skip-list**
   (files/globs the tool must never touch), not line-level merge — coarser than Copier. `cruft
   check` gives a CI-friendly drift signal. [docs](https://cruft.github.io/cruft/).
3. **Yeoman generator re-run** — per-file interactive conflict prompt (overwrite/skip/diff/
   overwrite-all), no line-level merge. Documented (via open GitHub issues) to clobber user-added
   code and to break down specifically in non-interactive/CI contexts.
4. **Framework-native "diff two blank generations"** (Rails `app:update`, React Native Upgrade
   Helper) — diff two *template* states against each other, not project-vs-template. Rails
   presents it as an interactive per-file prompt; RN's Upgrade Helper is a pure diff viewer with
   **no apply step at all**. Practitioner write-ups warn against trusting the automated prompt and
   recommend cherry-picking by hand instead — least automated of the four.
5. **Git subtree/submodule** — generic history-merge, not template-aware; no distinction between
   template-owned and project-owned content. Real usage needs custom wrapper scripts around raw
   subtree/submodule commands.

**Scoping takeaway:** the field splits on two axes — (a) diff granularity: line-level merge
(Copier) vs. file-level skip-list (cruft) vs. whole-file overwrite-or-skip (Yeoman) vs.
presentation-only (Rails/RN); (b) what gets diffed: project-vs-template directly (subtree/
submodule) vs. two template generations diffed against each other, then applied separately to the
project (Copier, cruft, Rails, RN) — the latter is the dominant, more mature pattern, since it
cleanly isolates "what changed upstream" from "what this project changed locally." No source
addresses our specific "many small sibling projects, agent-mediated, low human-review-budget"
constraint directly.

**Evidence gaps:** Ember CLI's `ember init` re-apply mechanism turned up no direct results
(unconfirmed, not fabricated). Cruft's conflict-resolution algorithm isn't documented beyond
"diff and review before apply" — no line-level conflict-marker equivalent found.

**Next:** evaluate these five against `docs/CONSTRAINTS.md` (solo dev + AI agents, prefer
agent-mediated automation) and the ticket's Musts, then reach a decision.
