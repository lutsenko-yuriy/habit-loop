# HAB-234: Welcome-back reminder for an unpersisted showup can survive a later, unrelated break's cancellation sweep

## Notes

### 2026-08-16

**WU scope summary**

- **WU1** (`feature/HAB-234-WU1-reconcile-break-service`) — `PactBreakService.reconcileWelcomeBackReminders({pact, breaks, now})` replaces `_scheduleWelcomeBackReminder`/`_revertWelcomeBackIfResumedEarly`. For each break's target (via `BreakDerivation.firstShowupAfterBreak`), cancel if another break now covers that date, else reschedule (auto-picks welcome-back vs standard text). Wired into `startBreak`/`stopBreak`. Fixes the reported bug: a later break's cancellation sweep now reaches earlier breaks' synthetic (unpersisted) targets.
- **WU2** (`feature/HAB-234-WU2-dashboard-reconcile`) — same method called from `DashboardViewModel`'s existing per-pact loop (Job 2, `_runGapFillSweepAndScheduleReminders`), which already has `breaksByPactId` fetched fresh every load. Fixes multi-device staleness for free — no new sync-layer coupling needed.

Full plan: HAB-234 Linear comment, posted 2026-08-15.

**Workflow friction: review-loop gate after PR open**

`docs/FEATURE_WORKFLOW.md` step 9 makes the review loop (step 10) wait for the user's explicit command after a PR opens, specifically to give room to check the running app first. On WU1 of this ticket the user asked to skip that wait — trigger the review loop automatically as soon as the PR opens, no separate go-ahead needed. Worth revisiting at debrief time whether the gate should default to on, or become opt-out.

**Comments still too wordy — repeat feedback**

Despite [[feedback_code_comment_brevity]] already being logged, WU1's code comments (the `reconcileWelcomeBackReminders` docblock, the `clearStoppedAt` probe comment) came out multi-paragraph again, and the user called it out a second time on this same ticket. The existing memory's guidance ("one concise line per comment; if it takes more than a glance to parse, cut it") isn't landing during first-draft writing — it's only getting applied on explicit prompting. Consider applying it as a self-check pass before presenting code, not just as a recalled fact.

### 2026-08-16

**WU2 audit findings — 2 real critical bugs from a one-shot → periodic call change**

`audit-code` on WU2's PR (#382) caught two 🔴 bugs that WU1's own tests never exercised because `reconcileWelcomeBackReminders` was one-shot (called once, at mutation time) there — WU2 made the same call periodic (every dashboard load), which is what turned two latent weaknesses into standing conditions: (1) the derived welcome-back target is always synthetically `pending` (never reflects the persisted row's real status), so a completed showup got re-reminded on every subsequent load; (2) passing `now: todayNorm` (midnight) let a same-day target always qualify as "future", so Android fired the alarm immediately on every dashboard open instead of at the scheduled time. Both fixed in-PR; both regression-tested. Worth remembering for future "make an existing one-shot call periodic/looped" changes: re-audit every guard the call relies on for what it assumes about *when* it's called, not just *what* it does.

Also noted: I initially called the `Skill` tool for `audit-code` without following through with the actual `Agent` spawn its own instructions require — it silently loaded the skill text but never ran anything, and only the user's follow-up question ("Was it even started?") caught it. Worth a habit check: after invoking a skill whose own instructions say "route to a subagent," confirm the `Agent` call actually happened in the same turn, not just that the `Skill` tool returned.

## Debrief summary

### 2026-08-16

**What went well**
- The stateless `reconcileWelcomeBackReminders` design (shared by `startBreak`/`stopBreak`/dashboard-load) turned out clean enough to consolidate two asymmetric one-shot helpers into one symmetric method — praised in architecture review, no complaints on the shipped design itself.
- Fixing low-effort review/audit findings immediately, in-PR, rather than deferring — both WU2 audit rounds resolved same-session.

**What was hard or surprising**
- Making a previously one-shot call (`reconcileWelcomeBackReminders`, called once per mutation in WU1) periodic (every dashboard load, WU2) turned two latent weaknesses — a synthetic-target status check and a midnight-normalized `now` — into standing, reachable bugs. WU1's own tests never exercised either because the call only ever ran once, near the mutation. Neither was visible without `audit-code`'s pass.
- Comment brevity feedback recurred a third time (HAB-207/208, then twice here) despite an already-logged, already-strengthened personal-assistant memory — the guidance never made it into a project doc as a checkable rule, only assistant-side memory. Filed HAB-235 to research concrete thresholds before writing anything into `docs/CODE_STYLE.md`.
- A "route this skill to a subagent" instruction was followed only halfway: the `Skill` tool call returned confirmation text, and that was mistaken for the actual `Agent` spawn completing — it hadn't. Caught only because the user asked directly whether it had started.

**What to change**
- `docs/FEATURE_WORKFLOW.md` step 9/10: the review loop now starts automatically once a PR opens, instead of waiting for explicit go-ahead — opt out explicitly if you want to check the running app first.
- `skills/shared/decision-guidelines.md`: added a guideline to verify a delegated subagent spawn actually happened (agent ID/tool result) before treating a "route to subagent" step as done.
- HAB-235 opened to research code-readability thresholds (comment length, function/class size, PR size/span) for eventual `docs/CODE_STYLE.md` codification.
