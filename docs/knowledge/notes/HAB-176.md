# HAB-176: Reduce token consumption from Linear MCP interactions

## Notes

### 2026-08-10

**Fixed-cost premise from v1 plan was wrong — corrected in v2**

v1 estimated the 53 `mcp__linear__*` tool schemas cost ~12–18k tokens per session (fixed, present regardless of field-trimming). This is false for this project's setup: Claude Code 2.1.220 with an Opus/Sonnet 4.5-generation model has **MCP tool search on by default** — only tool *names* load at session start, schemas load on demand via `ToolSearch`. Confirmed directly (this session received all 53 Linear tools as deferred names and had to call `ToolSearch` before invoking them), not just from docs. Real fixed cost is ~400–700 tokens, not 12–18k. This is the exact HAB-197/decision-guidelines §5 trap the v1 plan itself warned about — sizing a cost without checking whether it's actually paid. Keep this in mind for any future "how much does X cost the session" estimate: measure against a live transcript, don't infer from schema size alone.

**No genuine per-tool MCP filter exists for this repo's setup**

Investigated during WU4 planning: `disabledMcpTools`/`enabledMcpTools` don't exist in the Claude Code binary. The `blocked` tool-filter semantics that would help are a claude.ai *organization connector policy*, unreachable from a plain `.mcp.json` HTTP server like this repo's `linear` entry. `allowedMcpServers`/`deniedMcpServers` are `managed-settings.json`-only and server-level, not per-tool. `permissions.deny` on individual tool names is real and repo-owned but its effect on the deferred name list (vs. just blocking the call) is unconfirmed — that's what WU4's measurement step is for.

### 2026-08-10 (WU2)

**Live MCP fallback removed from `summarize`, not softened**

Resolved open question 3 from the original plan: `summarize`'s "fallback path" (live `list_issues`/`list_milestones` MCP calls, used when not routed via `skill_router.py`) is deleted outright, not merely narrowed. If the pre-fetched sentinel block is missing, the skill now tells the user the pre-fetch failed (most likely `LM_API_TOKEN`/`LINEAR_API_KEY` unset, or LM Studio down) instead of silently degrading to a live fetch. This trades away a safety net for keeping exactly one code path to maintain — accepted explicitly in the plan-approval comment.

**The "per-ticket `get_issue` loop" was in the `PLAN.local.md` survey step, not the main backlog step**

The v1/v2 plan's "step 2" reference predates step 0 (`PLAN.local.md` survey) being added to `summarize/SKILL.md` — by the time WU2 landed, the loop actually lived in step 0 point 2 (checking each `PLAN.local.md`-listed ticket's state one `get_issue` call at a time).

**Audit caught a real bug in the first WU2 draft, plus a better design**

First attempt replaced the per-ticket loop with a single `list_issues` call using `fields: ["identifier", "status", "statusType"]` — `identifier` is not a valid value in that tool's `fields` enum, so the call would have failed input validation on every `PLAN.local.md`-present session. Confirmed empirically (not just from the schema) that the always-included `id` field already returns the human identifier (`"HAB-176"`, not a UUID) on this workspace, so no field addition was even needed there. Separately, the audit pointed out step 0 was unreachable in the normal `skill_router`-routed path regardless of what the call looked like — `context: linear` and `tools:` are independent frontmatter keys, and `summarize` declares no `tools:` group, so the routed LM Studio session has no MCP access at all. Final design: step 0 matches `PLAN.local.md` tickets against the pre-fetched block already injected for step 1 (no live call at all in the routed path), falling back to per-ticket `Fetch issue` only when that block is unavailable (the Agent-fallback path). Lesson: verify a tool's actual accepted parameter values (or test the call) before writing a replacement, and check whether a step's assumed execution path can actually reach the tools it calls.

### 2026-08-10 (WU3)

**WU2's fallback deletion reverted — restored, not merely narrowed**

The 2026-08-10 (WU2) note above ("Live MCP fallback removed from `summarize`, not softened") is now superseded: live-session experience the same day showed the trade-off didn't hold in practice. A broken `skill_router` (this session hit both a `tomllib`-missing bug on the system `python3` and LM Studio being unreachable) left `/summarize` stuck asking the user to fix the script before showing any backlog at all, with the Agent-fallback path (`.claude/commands/summarize.md`) having nothing to fall back to. `summarize`'s live `list_issues`/`list_milestones` fallback and its step 1a product-vs-process classification are restored, now with an explicit one-line "using the slower live path" signal to the user and the same `fields`/`state`/`includeArchived` defaults as the pre-fetched path (WU1/WU2's field-scoping is not undone). See `skills/shared/linear-efficiency.md`'s "Correction" section for the durable version of this note. This entry is left in place rather than edited, per the note above being a historical record of what WU2 actually decided at the time.

## WU scope summary (plan approved 2026-08-10, revised same day)

- **No WU0.** Pure skill-instruction/doc changes — no Dart, no widget, no user flow. `draft-scenarios` has nothing to assert.
- **WU1** (`feature/HAB-176-WU1-efficiency-reference`, 3 files ~150 LoC, `[meta]`) — New `skills/shared/linear-efficiency.md` (field-selection defaults + minimum-viable-field-set table + the tool-search finding above, so it isn't re-derived later); `skills/shared/pm-tool-mapping.md` gains a **Default parameters** column; baseline measurements recorded in this file. Docs only, no behaviour change.
- **WU2** (`feature/HAB-176-WU2-call-site-fields`, 3 files ~65 LoC, `[meta]`) — **Highest-value WU, ~30k+ tokens off a session start.** Delete `summarize`'s per-ticket `get_issue` loop (step 2) — status comes from `list_issues` + `fields`/`state` filter instead; delete `summarize`'s live MCP-fallback branch entirely, leaving the `skill_router` pre-fetched path as the only path; collapse `ship`'s two adjacent `get_issue` preconditions (steps 22/24) into one; add explicit `fields`/`limit`/`includeArchived: false` to `list_issues` calls in `summarize`/`brief`.
- **WU3** (`feature/HAB-176-WU3-session-reuse`, 7 files ~80 LoC, `[meta]`) — Fetch-once/reuse-from-transcript convention added to `linear-efficiency.md` (including a "compaction resets reuse" clause); "reuse if already in transcript, re-fetch if stale" precondition added to the issue-fetch step of `analyze`, `plan`, `draft-scenarios`, `implement`. Also, discovered live this session: WU2's deletion of `summarize`'s live-MCP fallback is reverted — see the WU3 note above.
- **WU4 — deferred, not dropped** (`feature/HAB-176-WU4-mcp-tool-hygiene`, 3 files ~50 LoC, `[meta]`) — Config-only: measure whether `permissions.deny` on unused tools drops them from the deferred name list; if so, deny the ~41 unused ones (53 total minus the 12 already allowlisted in `.claude/settings.local.json` — corrected during WU1 review, see PR #367); regardless, deny destructive-but-unused tools (`merge_diff`, `delete_comment`, `delete_attachment`, `delete_status_update`, `submit_diff_review`) as a safety guard; document that the `linear` server must never gain `alwaysLoad: true`. No token-savings rationale left (see note above) — its value is pure safety/hygiene. Decision on whether to build it is postponed until after WU2 ships.

Test strategy per WU: WU1 is the measurement itself (recorded here, reproducible); WU2 verified by dry-running `/summarize` pre/post and confirming identical backlog content with a smaller payload; WU3 verified by dry-running one ticket lifecycle and counting `get_issue` calls before/after; WU4 (if built) verified by the name-list measurement plus confirming denied tools actually refuse to run. `flutter analyze`/`flutter test` are not meaningful evidence here — nothing under `lib/`/`test/` changes.

## Debrief summary

### 2026-08-11

**What went well**
- The ticket went relatively well overall.

**What was hard or surprising**
- Spent more effort than the ticket warranted, and in hindsight it should have been prioritized earlier. No concrete triggering signal was identified to turn this into a reusable prioritization rule — noted as a one-off observation.

**What slowed things down**
- It wasn't clear upfront how to test the changes — this ticket's plan had a prose "Test strategy" paragraph but no concrete, checkable steps, so verification happened ad hoc (dry-running `/summarize`, manually reasoning through the audit findings) rather than against a plan set in advance.

**What to change**
- `plan` now always produces a WU0, even when a ticket has no user-facing flow for `draft-scenarios` to assert against: either integration scenarios (unchanged, when `AppHarness` applies) or a **verification checklist** — concrete, ticket-specific checks, each tagged **[agent]** (the agent runs it itself) or **[human]** (needs a person's judgment). `implement` now has a step (8.5) that runs every [agent] item and asks the user to confirm every [human] item before the final WU's PR opens, so the checklist gets executed rather than just written and forgotten. Applies to any ticket where scenario generation is skipped, not just meta/skills ones. Changed: `skills/design/plan/SKILL.md`, `skills/design/plan/resources/plan-template.md`, `skills/build/implement/SKILL.md`.
