**Research-WU findings: does `pendingNotificationRequests()` reliably survive a cold restart?**

Thesis/antithesis literature research (2 parallel search subagents + synthesis) found no verified, first-party evidence directly settling "does `pendingNotificationRequests()` lose entries scheduled in a previous session, across a cold restart" on either platform. What the evidence *did* show, reframing the original concern:

- The query API's own bookkeeping tends to survive restarts on both platforms — two verified Android GitHub issues ([#2412](https://github.com/MaikuB/flutter_local_notifications/issues/2412), [#2174](https://github.com/MaikuB/flutter_local_notifications/issues/2174)) show `pendingNotificationRequests()` continuing to correctly report an entry after a device restart/app relaunch, even in cases filed as bugs.
- The actual failure mode in those bugs was **delivery**, not the query list: an Android OS alarm not surviving reboot (needs a `BOOT_COMPLETED` receiver to re-arm), separate from what the API reports.
- No verified iOS source substantiates cold-restart data *loss* in `pendingNotificationRequests()` specifically. Verified iOS bugs found were a stale null-safety crash ([#1287](https://github.com/MaikuB/flutter_local_notifications/issues/1287)) and the documented 64-pending-notification cap silently dropping anything past it ([#2312](https://github.com/MaikuB/flutter_local_notifications/issues/2312)) — a different failure shape than "loses entries after restart."
- Evidence was thin overall: no Apple-docs page could be fetched with real body content (JS-rendered), no AlarmManager/WorkManager official docs fetched, several leads were snippet-only and unverified.

**Conclusion for WU2/WU3 design:** the plan's `[human]` on-device cold-restart verification item (Test Strategy, WU3) stays necessary — literature research found no substitute for actually checking this codebase's own `flutter_local_notifications` usage on a real device. Slight lean toward not over-committing to a strict diff-only design until that check confirms the assumption; the documented fallback (unconditionally re-apply the desired plan, skipping the diff) remains the right hedge if the device check reveals gaps.

### 2026-08-26

**WU2 review findings (both review-architecture and audit-code, PR #411)**

Two real correctness bugs caught and fixed before merge:

- The cancellation criterion was "not in the desired set ⇒ cancel everything for this showup" — but `ReminderPlanner`'s desired set also excludes a showup simply *in progress* (its reminder fire time already passed), whose deadline/hurry-up notifications are still legitimately pending. Since `cancelShowupReminder` cancels all three ids at once, this would have silently killed a showup's deadline/hurry-up notification the moment its reminder fired, once WU3 wires the foreground trigger. Fixed: cancel only when a showup is *genuinely* no longer eligible for any notification (done/failed, or now on-break) — the actual case this ticket exists to fix.
- The iOS 64-notification budget is spent per `ReminderPlanner.plan()` call, but `reconcile()` calls it once per active pact — N active pacts could together request N×64 against one shared OS-level cap, with the silently-dropped overflow read as "missing" and rescheduled forever. Fixed: `plan()` now takes an optional `budgetCeiling`, and `reconcile()` shares one running budget across pacts.

A third finding (iOS's `getPendingNotifications()` possibly being session-scoped, per this repo's own doc comments) was **not** fixed blind — it's the same open question the Research-WU already flagged and explicitly deferred to a `[human]` on-device check. Restored/strengthened the caveat in `ARCHITECTURE.md` instead of guessing a redesign ahead of that data; replied to the review comment explaining this. If the WU3 device check confirms it, cancellation-on-iOS-after-cold-start needs a real design decision then, not a WU2 patch.

**4th v1 scope guard (documented, not fixed):** stopped pacts and pacts whose `reminderOffset` was cleared are excluded from `reconcile()`'s whole pass (mirrors `getActivePacts`), so any stale notification belonging to one is unreachable to this mechanism — those paths already cancel explicitly on the mutation that stops/clears them, so this is believed low-risk, but flagged per audit's suggestion.

**For debrief: add the kill switch in the first WU, not WU2**

The plan sequenced `notification_reconciliation_enabled` into WU2 (alongside `NotificationReconciliationService` itself). In hindsight the kill switch should ship with WU1 — the first WU that lands any part of the mechanism — so there is a working off-switch from the moment any of this code reaches `main`, rather than a window where the feature is partially built with no way to disable it remotely if something goes wrong. Revisit WU-sequencing guidance for future multi-WU tickets: land the kill switch in whichever WU is first to touch runtime behavior, not wherever the "main" service happens to land.

### 2026-08-26 (continued)

**WU3: `tester.pump()` hangs forever while `AppLifecycleState.paused` on host integration tests**

While writing the idempotence scenario (`reconciliation_is_idempotent_across_repeated_foregrounds`), triggering `tester.binding.handleAppLifecycleStateChanged(AppLifecycleState.paused)` and then calling `await tester.pump(...)` hung indefinitely on host (`flutter test integration_test/...`, no `-d`) — confirmed via bisection with temporary debug prints: `NotificationReconciliationService.reconcile()` itself completed instantly, the hang was purely in the next `pump()` call. Root cause: `LiveTestWidgetsFlutterBinding` (used on host, unlike the fake-clock `WidgetTester` binding plain `flutter_test` widget tests get) awaits a real engine frame, and Flutter deliberately withholds frame scheduling while the app's lifecycle state is `paused` — same as a real backgrounded app not rendering. There is nothing to pump to.

Fixed by not pausing at all — the scenario only needed two `resumed` events back-to-back, which doesn't exercise this path. **Takeaway for future integration tests:** never call `tester.pump()` (with or without a duration) right after driving `AppLifecycleState.paused` on host — if a scenario genuinely needs to assert paused-state behavior, drive it through `AppLifecycleState.inactive`/no pump, or run on a real device/emulator instead, where the platform still delivers frames test-side.
