**Survey — "robot pattern" precedent in the Flutter ecosystem**

Topic-mode research (no thesis to adjudicate). Evidence:

| Source | Type | Finding |
|---|---|---|
| [VGV — "Readable Robot Tests"](https://www.verygood.ventures/blog/robot-testing-in-flutter) | Vendor eng blog | One robot class per screen, exposing user-level actions (`enterEmail`, `tapLoginButton`) that hide `find`/`pump`/`tap` details |
| [VGVentures/robot_testing](https://github.com/VGVentures/robot_testing) | OSS example repo | Low confidence — predates `integration_test` package (still `flutter_driver`), content not fully rendered |
| [Patrol GitHub Discussion #1460](https://github.com/leancodepl/patrol/discussions/1460) | Maintainer/community discussion | Maintainer groups tightly-related screens into one Page rather than strict 1:1; separately recommends centralizing widget `Key`s in one file shared by app + test code, to kill typo-class bugs |
| [pub.dev `flutter_robot`](https://pub.dev/packages/flutter_robot) | Indie package | `{screen}_robot.dart` naming convention, but only 3 likes/42 downloads — not evidence of real adoption |
| [Polymorph — "pump and unsettle"](https://polymorph.co.za/software-engineering-and-technology/flutter-integration-testing-pump-and-unsettle/) | Practitioner blog | Concrete failure mode: `pumpAndSettle()` hangs on any looping animation; fix is a bounded `pump(duration)` — matches our own `widget-test-gotchas.md` entry |

Conclusions: the "robot pattern" is a real, named Flutter-community convention (VGV, LeanCode/Patrol) but not an official Flutter/Dart-team one — nothing in flutter.dev's own docs endorses it. No source found packages a *specific* fix for our actual pain points (keyboard-inset relayout races, lazy-list/offstage scroll realization) inside a robot method — the pattern solves **naming/organization** (intention-revealing methods per screen), not **timing**. Timing fixes still use the same primitives we already have (`pump(duration)`, `ensureVisible` sequencing); the payoff of a robot layer is centralizing "fixed once" instead of "copy-pasted per test." One transferable idea not yet in our own practice: centralizing widget `Key`s in one file shared between app and test code (Patrol discussion #1460).

User's own read on this: HAB-258's fix already followed VGV's Source #1 shape in substance (shared, intention-revealing helpers like `_waitForNoteSaved`, `_enterNoteText` inside `pact_note_flow_test.dart`) but stopped short of lifting that logic into a separate reusable class — i.e. the pattern was reinvented ad hoc, per-file, rather than adopted as a standing convention.
