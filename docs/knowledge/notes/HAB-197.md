# HAB-197: CI: let scenarios.yml target a single test file/tag instead of the full suite

## Notes

## Debrief summary

### 2026-08-03

**What went well**
- Even though the ticket itself was canceled, live-dispatch verification produced a clear, useful answer: the potential savings from scoping to a single test file are negligible, and running the full suite still makes more sense. Ruling that out is a good outcome, not a wasted one.
- The interactive design discussion (single-select `choice` dropdown with human-readable labels instead of free-text paths) landed on a more user-friendly design than the initial free-text/tag idea.

**What was hard or surprising**
- The initial design would have required remembering/typing exact integration-test file names; discussing it surfaced a better design (a `choice` dropdown with human-readable labels mapped to filenames) before any code was written.
- The real surprise came from live dispatch: each scoped run still took ~6 minutes against a ~10 minute full-suite baseline — the Android emulator boot + APK build overhead (already visible in `run-scenarios/action.yml`'s existing steps) dominates regardless of how narrow the `flutter test` target is, so the whole premise of the ticket didn't hold up.

**What to change**
- For CI/process tickets whose goal is to speed up an existing workflow, decompose its current steps into fixed overhead vs. the portion actually being scoped, and estimate the fixed-cost share *before* building a design — not just after dispatching the finished thing live. Added as guideline 5 to `skills/shared/decision-guidelines.md`, with a pointer from `skills/design/plan/SKILL.md` step 2.
