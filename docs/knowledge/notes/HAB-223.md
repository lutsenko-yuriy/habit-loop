# HAB-223: Prevent silent bad auto-merges of docs/knowledge/notes/INDEX.md

## Notes

### 2026-08-16

**Plan scoped down to WU1 only; WU2 (CI self-heal push to main) dropped**

The approved plan originally had two WUs: WU1 (`ship`-time rebase+regenerate, closes the merge-race window in the normal path) and WU2 (`index.py --heal` + a `heal-notes-index` CI job pushing directly to `main` with `[skip ci]`, mirroring `version-tag`'s existing build-number-bump pattern). User declined WU2 specifically because it pushes to `main` without a PR, and raised a broader question: should CI ever push directly to `main` at all — including `version-tag`'s existing build-number bump, not just this new job? That's out of scope for HAB-223 (a load-bearing, documented part of the release pipeline, not local to this ticket) — captured as a new ticket instead of folded in here. HAB-223 proceeds as WU1 only.

**`block-main-writes.sh` false-positives on commit messages that merely mention "push"/"main" in prose**

While committing WU1's audit-fix follow-up, a plain `git commit -m "..."` (no push at all, branch was the feature branch) was blocked with "this push targets main". Root cause: the hook's pattern-1 check (`.claude/hooks/block-main-writes.sh`) does `grep -qE '\bpush\b'` and a separate `main` match over the **entire Bash tool_input.command string** — including the literal text of the `-m` commit message — not just the actual git subcommand being run. A commit message describing "step 9's git push" and "origin/main" in prose (exactly the kind of message this very ticket's fix produces) trips both patterns even though no push is happening. Worked around with `git commit -F <file>` instead of inline `-m`, which keeps the message text out of the scanned command string. Not fixed here — out of this ticket's charter (notes-index staleness, not hook tooling) — but worth a follow-up ticket since the workaround (external file) isn't something every session will think to reach for.

## Debrief summary

### 2026-08-16

**What went well**
- The plan's dry-run checklist item caught a real ordering bug before it ever reached a PR — regenerating the notes index right before commit looked fine on paper, but only actually rebasing *first* (before any of `ship`'s own edits) avoids `git rebase` refusing an uncommitted tree.
- The audit loop then caught four further genuine issues the dry-run didn't exercise: a bare `git push` that would fail non-fast-forward whenever the rebase actually did anything, no conflict-handling on the rebase itself, a contradiction between step 2's clean-tree assumption and step 9's existing allowance for unstaged `/note` edits, and a missing `--check` validation gate given `main` has no branch protection.
- Scoping down from 2 WUs to 1 mid-planning (dropping the CI-pushes-to-main WU2) and spinning the broader question out as HAB-237 kept this ticket tight instead of ballooning into a policy debate.

**What was hard or surprising**
- Hit a real false-positive in `.claude/hooks/block-main-writes.sh`: a plain feature-branch commit was blocked because its own commit message *described* a push/main fix in prose, not because it actually pushed to main. Worked around with `commit -F`; filed as HAB-238 rather than fixed inline, since it's unrelated to this ticket's actual subject.

**What to change**
- Nothing new for this workflow — HAB-237 and HAB-238 already capture the two follow-ups that came out of this ticket.
