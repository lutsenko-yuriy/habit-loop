# HAB-209: Postmortem: find when/why stop-pact started deleting ALL showups

## Notes

### 2026-08-16

**Origin: PR #21 (commit 3728387, 2026-04-18) — deliberate design, not an accident**

`git log -S"deleteShowupsForPact"` traces the behavior back past both HAB-11 WU3 (`afc0d35`, which only wrapped an *already-existing* two-step delete in a transaction) and HAB-11 WU4 (`75b2b56`, which only swapped the in-memory repo for SQLite) to the true origin: PR #21, "[codex] Fix pact stats persistence and dashboard analytics" (2026-04-18, authored via Codex — the one PR in this file's history not co-authored by a Claude model). `PactStatsService.stopPact` was introduced there already deleting all showups on stop, deliberately: the commit paired the deletion with a **frozen `PactStats` snapshot** written onto `pact.stats` *before* the delete, with an explicit comment: "Returns fresh stats whenever showups still exist, falling back to the persisted snapshot only after the showups were deleted (stopped pact)." Delete-all was never an oversight — the author designed a safety net for it up front.

**Detection gap: the safety net was silently amputated three weeks later, with nothing to notice**

HAB-11 WU2 (commit `541db06`, 2026-05-05, SQLite persistence) introduced `PactMapper.fromRow`/`toRow` and made a *separate*, seemingly reasonable call: `pact.stats` is "not persisted — always computed from SQL aggregates at read time," so `fromRow` always returns `stats: null`. That decision, on its own, looks fine for an *active* pact (stats recompute from its live showups). But it silently deletes the one thing PR #21's stopped-pact fallback depended on — nobody at WU2 time connected "stats null on every load" back to "the stopped-pact snapshot must survive a load or the fallback in `currentStats` is dead code." Neither PR's tests would have caught the interaction: HAB-11 WU3's `pact_transaction_service_test.dart` (which does assert "all showups deleted") builds its `Pact` objects directly in Dart and calls `stopPactTransaction` on them — it never round-trips through `PactMapper.fromRow`, so a test that faithfully encoded the delete-all *contract* had no way to see that the contract's own safety net was broken elsewhere. The gap wasn't a missing assertion in one test — it was two correct-in-isolation decisions, three weeks apart, with no test spanning both.

**Answering the ticket's item 3 directly:** yes, `stopPactTransaction`'s test asserting "all showups deleted" as expected/passing is real (confirmed at introduction in `afc0d35`, reason string literally says "pending showups must be deleted on stop" while deleting unconditionally) — but that alone is not the story. The test was *correctly* encoding PR #21's real, deliberate design; the design was reasonable *conditional on* the stats snapshot working. The actual regression is that the snapshot silently stopped working and nothing re-validated the conditional. HAB-208's fix sidesteps this entirely by no longer relying on a frozen snapshot — past/resolved showups just stay in the table.

**Proposed prevention (sized to the actual gap, not a blanket policy)**

The specific failure mode here is: a persistence-layer decision ("don't persist X") silently invalidates an assumption an *unrelated*, earlier feature depended on, with no test exercising the two together. A blanket "add more integration tests" policy is too broad. Narrower, actionable version: when a domain model gains a field that's computed/nulled at the mapper boundary (`fromRow` returning `null`/a default for something the constructor accepts), grep for other read sites of that field across the codebase before merging — `pact.stats` had exactly one real consumer (`currentStats`'s fallback branch) and a one-line grep at WU2 time would have surfaced it. This is cheap enough to be a review-checklist item, not a new test-infrastructure investment.
