**Cross-WU invariant reminders**

- "At most one successor" is enforced at the data layer (partial unique index + `savePact` guard), not just by hiding the button — per the approved architectural decision.
- The version-number default name is computed once at creation from the chain root, never recomputed; renaming any pact later does not retroactively change others.
- No stats/streak carryover — the chain is purely navigational/informational.

**Open risk — concurrent-creation sync conflict (from WU1 audit, PR #338)**

If two offline devices each create a successor to the same predecessor, the `savePact` guard/unique index correctly reject the second one locally — but on Firestore pull-merge, the rejection is silently swallowed by the per-record try/catch (`firestore_sync_service.dart` `_mergeRemotePact`, pull loop). The skipped record never becomes locally dirty, so it's never retried: one successor permanently never lands on other devices, even though it still exists in Firestore and on its origin device. Not reachable until the chaining UI ships (no blocker for WU1/WU2), but needs a conflict-resolution rule designed **before WU3**. Leaning toward last-write-wins as the simplest option — see the product-direction note below on why a more elaborate rule likely isn't worth designing yet.

**Product-direction note (2026-07-29): possible future generalization to a directed graph**

Discussed while triaging the above: the current ticket explicitly scopes the chain relationship as strictly linear (at most one successor — see "Out of scope" in the ticket body), but there's a standing intent to possibly generalize this into a directed graph (multiple successors / branching) in a later ticket. This is **not** in scope for HAB-202 and nothing here should be built to anticipate it — flagging only so the WU3 conflict-resolution design (and any other one-successor-shaped decision) is made with "cheapest reasonable option, likely to be discarded on a future graph generalization" in mind rather than over-engineered now.

**Leading WU3 design candidate: resolve the sync conflict by clearing the loser's link, not dropping the record**

Today `predecessorPactId` is immutable after insert (no `copyWith` param, excluded from `PactMapper.toUpdateRow`) — deliberate, matching the ticket's "Out of scope: any way to delete/edit/break an existing chain link once created." That's correct for WU1's insert-time guarantee, but it means the concurrent-creation conflict above (two devices each create a successor to the same predecessor) currently has no graceful resolution: the losing pact's whole record silently never reaches other devices, so a user could end up with a parent that appears to have a successor, but a different successor pact exists elsewhere that's simply invisible.

Leading candidate for WU3: make `predecessorPactId` clearable — add a `clearPredecessorPactId` flag to `Pact.copyWith` (same pattern as `clearReminderOffset`/`clearStopReason`) and include `predecessor_pact_id` in `toUpdateRow`. On a detected conflict, null out the losing pact's link instead of discarding the record: the pact itself is never lost, it just surfaces as an unlinked/root pact rather than disappearing. Simplest rule for picking the "loser": last-write-wins (see the directed-graph note above for why a more elaborate rule probably isn't worth designing against today's one-successor constraint). This reverses WU1's immutability invariant deliberately and only for this one path — leave WU1's code as merged; do not preemptively add the `copyWith`/`toUpdateRow` mutability now.

**Debugging note (2026-07-30): apparent test "hang" was a 74-year pact span, not a real deadlock**

While validating WU3's two navigation-stack integration scenarios (`pact_chain_test.dart`) on an iOS simulator, `flutter test` appeared to hang indefinitely partway through `AppHarness.create()` — no crash, no timeout, no further output, reproduced identically across multiple runs (including with `--timeout`, which does not reliably bound on-device integration test execution). A control run of an unrelated, already-passing suite (`archive_pact_flow_test.dart`) completed normally in 12s on the same simulator, ruling out a broken environment. Root cause: the scenario's fixtures used `startDate: DateTime(2026, 1, 1)`/`DateTime(2026, 3, 2)` without an explicit `endDate`, and `harness.dart`'s `buildPact()` defaults `endDate` to `DateTime(2099, 12, 31)` — every *other* fixture in the suite anchors `startDate` near 2099 specifically to keep this span short (a convention that was never written down). A near-term `startDate` combined with that far-future default produced a ~74-year pact, and something on the dashboard/detail load path (not yet identified precisely — likely `ShowupGenerator` enumerating tens of thousands of daily occurrences) made that expensive enough to look indistinguishable from a real deadlock. Fix: gave both fixtures an explicit near-2099 `endDate`. Two follow-on assertion bugs surfaced once the "hang" cleared: (1) `find.text(habitName)` matched both the visible detail screen's title and the pacts-panel row still mounted underneath it (Navigator's default `maintainState: true`) — replaced with a helper reading the topmost mounted `PactDetailScreen.pactId` directly; (2) a fixed-duration `pump()` after tap wasn't always enough for a push/pop transition to fully finish before the assertion ran — replaced with `pumpAndSettle()`. Also added a pact-specific key (`pact-detail-scroll-view-<id>`) to both platform pages' outer `ListView` so a scroll-into-view helper can target the correct screen's own scrollable when multiple `PactDetailScreen`s are mounted at once (predecessor push/pop stacking).

**Process observation for debrief**: the "buildPact's default endDate forces near-2099 startDates" convention should be written down (a doc comment on `buildPact` itself, or a line in `docs/ARCHITECTURE.md`'s testing section) — it cost significant debugging time to discover empirically rather than by reading a comment.

**Real regression caught by re-running WU3's own scenarios**: the first cut of the bottom action area added a `Divider()` above the button/link for visual grouping (matching the active-pact "Take a break"/"Stop pact" section above it). This pushed "Next Pact" past the reachable scroll extent on a short iOS-simulator viewport, breaking both of WU3's nav-stack scenarios (a real, deterministic failure — not flakiness; re-running in isolation confirmed it). Removed the divider entirely rather than adjusting spacing, since it wasn't required by the ticket spec and the original "Next Pact" block's exact height had already been calibrated. **Lesson**: any change to a widget already covered by passing scenarios should re-run those scenarios before considering the change done, even when the change looks purely additive/cosmetic — see `docs/FEATURE_WORKFLOW.md`'s existing "opportunistic changes" guidance, which this reinforces rather than contradicts.

**Integration-test authoring gotchas found while driving the 5 stubbed scenarios green (all in `pact_chain_test.dart`, all fixed in WU4, none are product bugs):**
- The wizard's AppBar/nav-bar title shows the **habit name itself** once non-empty (not a generic "New Pact" title) — a prefilled flow's title and its `TextField`/`CupertinoTextField` show the *same* text simultaneously, so `find.text(prefillValue)` matches both ambiguously. Read the field's `TextEditingController.text` directly instead.
- `WidgetTester.dragUntilVisible`'s loop condition is "finder not found *at all*" (`finder.evaluate().isEmpty`) — if the target already exists anywhere in the tree (even off-screen, even behind another mounted screen), it performs **zero** drags. It is not a "scroll until the exact tap-center point is on-screen" guarantee; a target that technically "exists" per this check can still fail a subsequent `tester.tap()` if its computed center point isn't actually reachable.
- A route push/pop's **transition animation** can still be mid-flight the instant `waitFor` first finds the new screen — a keyed finder (e.g. a nav-bar button) can transiently match twice (outgoing + incoming bar) until `pumpAndSettle()` drains the animation. `.last`-tolerant reads (habit-name field) survive this; exact-count assertions on a keyed widget do not.
- A `PageView` forward swipe occasionally didn't cross the snap threshold on one specific hop (reminder→summary) even though the identical drag succeeded on every other page — empirically fixed with a generous safety margin (8 attempts for 5 real transitions; harmless since swiping past the last page is a no-op), root cause not fully isolated.
- The **same `PactDetailScreen` instance**, never disposed across a push-then-pop round trip (e.g. opening the wizard and cancelling out), keeps its `ListView`'s scroll position. If the list was scrolled to the bottom before the round trip, top-of-list content (the habit-name row) may not even be *built* yet on return (lazy list, not just visually offstage) — reading an unambiguous state field (`PactDetailScreen.pactId`, already established by WU3) is more robust than relying on scrolled-into-view text.

**Operational follow-up still open**: per the Remote Config sync-gap note below, flipping `RemoteConfigDefaults.pactChainingEnabled` to `true` in code does **not** change the *live* Firebase console value — that was manually set to `false` during WU3's console setup and needs a manual flip too (same throwaway `-c` config + `firebase deploy --only remoteconfig` procedure used to backfill `pact_breaks_enabled`), or the feature stays off in production despite the code-level default.

## Process observations (for debrief)

- **Mid-implementation scope corrections that touch scenarios get their own inserted WU, named `WUN-<short-correction-slug>` (not a decimal like `WUN.1`), not folded into the current or the next WU.** `WU0-scenario_correction` (navigation-stack scenarios, added before WU1 started) is the first instance. Generalized rule: if a correction surfaces *during* WUN's implementation and it changes what a scenario should cover, the fix lands in a new `WUN-<short-correction-slug>` branch/PR (e.g. `WU2-scenario_correction`) between WUN and WU(N+1) — never retrofitted into WUN's own commits (which may already be reviewed/merged) and never deferred into WU(N+1) (which has its own unrelated scope). Candidate workflow update: propose adding this as an explicit rule in the "Multi-WU tickets" appendix of `docs/FEATURE_WORKFLOW.md` at debrief time.
- **New kill-switch defaulting to `false` during a multi-WU rollout, flipped to `true` only in the final WU right before it ships.** User instruction (2026-07-29) for `pact_chaining_enabled`: since the toggle's gated UI (chain links in WU3, action button in WU4) is incomplete until the final WU, default `false` avoids exposing a half-built feature between WU3 and WU4 merging, even though in this specific case no user data could actually reach the half-built state yet (no pact gets a `predecessorPactId` until WU4's button exists). Candidate workflow update: consider whether `docs/FEATURE_TOGGLES.md` or the "Feature toggle" planning gate (`docs/FEATURE_WORKFLOW.md` step 1.4) should default to `false`-until-complete generally for any toggle introduced before its final WU, rather than defaulting new toggles to `true` universally.
- **Integration scenarios need a hard timeout — a genuinely stuck run is indistinguishable from a slow one without one.** User observation (2026-07-30), surfaced while validating WU3's navigation-stack scenarios: a `flutter test -d <device>` run that's actually hung produces no error, no crash, and (per HAB-202's own debugging session) took 20-30+ minutes of wall-clock time to diagnose locally before the true cause (an oversized pact-date fixture, not a real deadlock) was found — and the ticket notes this has also happened on CI, requiring a manual job cancellation. `--timeout=<n>s` does not reliably bound on-device integration test execution (confirmed empirically this session — it did not fire even when a run was genuinely stuck past the configured value). Candidate workflow update: investigate a wrapper-level timeout for `run-scenarios`/local scenario runs (e.g. shell-level `timeout` around the `flutter test` invocation, distinct from the test framework's own `--timeout` flag) so a stuck run fails fast with a clear "possible hang" signal instead of silently consuming the CI job's full 90-minute budget or a developer's unbounded local wait.
- **WU dependency triage: check whether one planned WU is a hard prerequisite for a later WU's own tests before finalizing the WU sequence.** User observation (2026-07-30): HAB-202's plan already sequences WU1 (schema) → WU2 (application logic) → WU3 (UI) correctly by necessity, but the pattern of a correction being *discovered mid-flight* (`WU0-scenario_correction`, inserted before WU1 started once the nav-stack rule was identified as needed) suggests planning should explicitly check, for every WU, whether anything it needs to make its own scenarios pass is missing from an earlier WU — surfacing that as a sequencing question at planning time rather than as a runtime scope correction. Candidate workflow update: add an explicit cross-WU dependency check to the `plan` skill's multi-WU output (e.g. "does WUN's scenario list require anything not yet built by WU1..N-1?") before the plan is presented for approval.
- **Remote Config has no repo-tracked/declarative sync process — new kill-switches only exist in Firebase if someone manually adds them.** Discovered 2026-07-30 while adding `pact_chaining_enabled` to the live console (user request): `pact_breaks_enabled` (HAB-195, shipped and merged weeks earlier) had never actually been added to Firebase at all — it silently ran on the in-app fallback default (`true`) this whole time, meaning that kill-switch was never actually remotely toggleable despite `docs/FEATURE_TOGGLES.md` documenting it as one. There's no `remoteconfig.template.json` committed to the repo and no CI/script step that syncs `RemoteConfigDefaults` to the live console (unlike, say, `scripts/firebase/cleanup_builds.py` for App Distribution) — adding a parameter required fetching the live template via `firebase remoteconfig:get`, editing it by hand, and publishing via a throwaway `-c` config pointing `firebase deploy --only remoteconfig` at the edited file, since `firebase.json` has no `remoteconfig` key and this CLI version exposes no direct `remoteconfig:publish` command. Backfilled `pact_breaks_enabled` at the same time (2026-07-30) so it's now actually live. Candidate workflow update: commit a real `remoteconfig.template.json` + wire a `remoteconfig` key into `firebase.json`, and add a step (to `ship` or a dedicated check) that flags when a new `RemoteConfigDefaults`/`featureToggleKeys` entry has no corresponding live console parameter — so this can't silently happen again for the next kill-switch.

- **Re-run scenarios already covering a widget before considering a cosmetic-looking change to it done.** WU4 observation (2026-07-30): adding a `Divider()` to `pact_detail_page_android/ios.dart`'s bottom action area looked purely additive but broke WU3's own nav-stack scenarios on a short viewport (pushed content past the reachable scroll extent) — caught only because those scenarios were re-run as part of driving WU4's own scenarios green, not because anything flagged the change as risky beforehand. Candidate workflow update: `docs/FEATURE_WORKFLOW.md`'s existing "opportunistic changes" guidance (write a test first for behavior changes) could explicitly call out that touching a widget already under integration-test coverage warrants re-running those scenarios even for changes that look like pure styling.
- **`WidgetTester.dragUntilVisible` is not a visibility guarantee — worth a project-level testing note.** WU4 observation (2026-07-30): its loop only checks whether the target `Finder` returns any match at all, so an already-present-but-off-screen (or behind-another-mounted-screen) widget causes zero scroll attempts, and a later `tester.tap()` can then fail to hit-test it. Every existing helper in this file (`_tapNextPactLink`, etc.) happens to work because the target is genuinely off-screen and not yet built — but this is worth documenting explicitly (e.g. a note in `docs/ARCHITECTURE.md`'s testing section or a doc comment on the helper pattern) so a future scenario author doesn't assume the helper's name implies more than it does.
